# planck_docker

A Docker Compose stack that runs Planck with private web search, workspace
indexing, document extraction, a credential proxy, per-agent memory, shared
task tracking, and skill capture — all wired up by one install script.
Designed to be installed once by a technical user for themselves or for
someone else. The same setup covers both local-only access (default) and
network-accessible server deployments.

This spec owns the **deployment view**: which containers run, how they're
wired together, directory layout, and configuration. It deliberately does
NOT re-describe what each sidecar tool or hook does in depth — that's:

- `specs/bundled-sidecar-tools.md` — full tool reference (what each tool does,
  its parameters, its LLM-facing description)
- `specs/sidecar.md` — hook mechanisms (compactor, prompt hook, turn-end hook)
  and how a custom sidecar plugs into the same points the bundled one does

## Use cases

- **Local workstation** — install on your own machine; access at `localhost:4000`
- **Someone else's machine** — install for a non-technical user; they open a browser, nothing else to configure
- **Home server** — expose on the local network so other household members can access it from their own devices

## Stack

```
Docker Compose
├── setup     (one-shot init: renders config templates, bootstraps agent-vault, copies the bundled sidecar; exits when done)
├── planck    (Elixir web UI + agent runtime + bundled sidecar, Node.js included)
├── searxng   (private meta-search — web_fetch/search_web)
├── typesense (workspace + session full-text index — search_workspace/session_search, per-agent memory)
├── tika      (document text extraction — read on binary files)
├── vault     (agent-vault: HTTPS credential MITM proxy)
├── dolt      (SQL backend for beads)
└── beads     (shared task-tracking API — bd_ready/bd_get/bd_done/bd_claim/bd_create/bd_delete/bd_list)
```

All services communicate on an internal Docker network. Only `planck:4000`
is optionally exposed on the host — every other service (including `vault`'s
management API on 14321) is internal-only, never published. All containers
run as UID/GID 1000 so files written to the workspace are owned by the user.

`setup` runs once to completion and exits — every other service depends on
it (directly or transitively) via `depends_on`. `planck` additionally
depends on `vault`, `beads`, `typesense`, `searxng`, and `tika` all being
started before it boots.

## Network access

Controlled by `PLANCK_BIND_ADDRESS` in `$HOME/planck/.env`:

| Value | Use |
|---|---|
| `127.0.0.1` (default) | Local only — no ports open to the network |
| `0.0.0.0` | All interfaces — accessible from other devices |

```yaml
# compose.yml
ports:
  - "${PLANCK_BIND_ADDRESS:-127.0.0.1}:4000:4000"
```

## Directory layout

```
$HOME/planck/
  .env                        ← generated on first install; edit to configure
  typesense-data/             ← workspace + session search index (bind mount, survives docker compose down)
  vault-data/                 ← agent-vault credentials, service rules, and CA cert (bind mount)
  dolt-data/                  ← beads' SQL backend data (bind mount)
  beads-data/                 ← beads service data (bind mount)
  workspace/                  ← mounted into the planck container as cwd
    doc_cache/                ← Tika-extracted text for binary files, keyed by sha256 of the source file
    .planck/
      config.json             ← written on first install only; preserved afterwards
      sidecar/                ← written on first install only; preserved afterwards
      searxng/settings.yml    ← rendered on first run; user-editable
      sessions/
      skills/                 ← user-managed + sidecar-written (SkillReflector)
      teams/                  ← user-managed
```

`~/.planck/` (the global Planck CLI config) is never touched.
The planck container's cwd is `$HOME/planck/workspace/`, so it picks up
`.planck/config.json` from there and never reads from `~/.planck/`.

To reset a service's data, stop the stack and delete the corresponding
`*-data/` directory.

## `.env` file

Generated by `install_docker.sh` on first install using an `add_if_missing`
pattern — existing keys are never overwritten, so re-running the install
script is always safe:

```bash
# $HOME/planck/.env
PLANCK_BIND_ADDRESS=127.0.0.1
TYPESENSE_API_KEY=planck-internal-key
SEARXNG_SECRET=<random, generated on first install>
AGENT_VAULT_MASTER_PASSWORD=<random, generated on first install>
AGENT_VAULT_EMAIL=admin@planck.local
AGENT_VAULT_PASSWORD=<random, generated on first install>
BEADS_TOKEN=<random, generated on first install>
```

Edit `PLANCK_BIND_ADDRESS` to `0.0.0.0` to expose on the network. Docker
Compose reads this file automatically — none of these values need to be set
by hand.

## Credential proxy — agent-vault

Agents never see API keys, even via the `bash` tool. [Infisical agent-vault](https://github.com/infisical/agent-vault)
sits between every outbound LLM/tool HTTP call and the internet as an HTTPS
MITM proxy that injects credentials by host-matching service rules — the
agent makes a plain, unauthenticated request; the proxy adds the right
header before it leaves the Docker network.

- **Port 14322** — the actual proxying port. `planck`'s `PLANCK_TOOL_PROXY=http://vault:14322`
  (plus `PLANCK_TOOL_PROXY_CA_CERT=/vault-data/ca/ca.crt.pem` for TLS
  interception) routes every outbound request through it.
- **Port 14321** — the management API. Never published to the host; only
  reachable from inside the Docker network. This is what credentials and
  service rules are actually stored/queried through.
- **Bootstrap** — the one-shot `setup` container registers agent-vault's
  owner account and creates a vault plus a scoped agent token
  (`AGENT_VAULT_TOKEN`), using `AGENT_VAULT_EMAIL`/`AGENT_VAULT_PASSWORD`
  from `.env`. `Sidecar.Secrets.AgentVault` (implementing `Planck.Agent.Secrets`)
  then talks to the management API with that token for every subsequent
  `store`/`fetch`/service-rule call.
- **One-time `.env` migration** — if a legacy `.planck/.env` or `~/.planck/.env`
  exists (the pre-agent-vault credential storage), `Sidecar.Secrets.AgentVault`
  parses its `KEY=value` lines as credentials and `# planck-service: host bearer KEY`
  / `# planck-service: host api-key HEADER KEY` comment lines as service
  rules, pushes them all to agent-vault once on startup, then deletes the
  `.env` file.
- **Managed via Planck's own UI** — credentials and service rules are
  configured through the Setup modal ("Manage secrets" / "Configure a
  service rule"), not a separate agent-vault admin surface.

## Sidecar configuration — `Sidecar.Config`

Every key below has a Docker-appropriate default; none need to be set for
the bundled stack to work, they exist for advanced customization.

## Searxng configuration

A `settings.yml.template` is bundled in the planck image. On first run the
entrypoint renders it via `envsubst` (substituting `SEARXNG_SECRET`) and writes
it to `.planck/searxng/settings.yml` in the workspace. The Searxng container
mounts that file, so the user can edit it directly in the workspace.

Users can customise Searxng through Planck via the `configure-searxng` skill.
The skill points agents to `.planck/searxng/settings.yml` and documents the key
options; agents use `read`/`edit` to apply changes. Run
`docker compose restart searxng` for changes to take effect.

## Planck Docker image

Built from this repository. Includes:

- Elixir/OTP/Mix
- Node.js (`@mozilla/readability` for `web_fetch`)
- The planck binary
- The bundled sidecar (written to workspace on first install only)

Runs as UID/GID 1000. Version is read from the root `VERSION` file.

The sidecar defines a `setup` alias in `mix.exs` that runs `mix deps.get` and
`npm install --prefix priv`. Planck's `SidecarManager` calls `mix setup` on
startup if the alias exists, falling back to `mix deps.get` otherwise. Sidecars
that don't need extra steps don't need to define the alias.

## Bundled sidecar — module inventory

A Mix project pre-installed in the planck image. Written to
`$HOME/planck/workspace/.planck/sidecar/` on first install only, preserved
on subsequent starts — the user can customise it freely. `Sidecar.Planck`
(the `Planck.Agent.Sidecar` entry point) grants the main agent 13 tools;
`list_skills`/`load_skill`/`write_skill` are only ever given to the
SkillReflector's own ephemeral mini-agent, never the main agent.

| Module | What it is | Detail |
|---|---|---|
| `Sidecar.Tools.Read` | Shadows the built-in `read` — binary files (PDF/DOCX/XLSX/etc, detected by content sniffing, no extension allowlist) go through Tika and are cached in `workspace/doc_cache/` | `specs/bundled-sidecar-tools.md` |
| `Sidecar.Tools.SearchWorkspace` | `search_workspace` tool — full-text search over indexed workspace files | `specs/bundled-sidecar-tools.md` |
| `Sidecar.Watcher` | Indexes the workspace into Typesense on startup, then watches for changes; also routes binary files through Tika before indexing | `specs/bundled-sidecar-tools.md` |
| `Sidecar.Tools.SearchWeb` | `search_web` tool — queries Searxng | `specs/bundled-sidecar-tools.md` |
| `Sidecar.Tools.WebFetch` | `web_fetch` tool — fetches a URL, strips noise via `@mozilla/readability` (Node.js, invoked through `erlexec`), returns clean Markdown; cached in Typesense | `specs/bundled-sidecar-tools.md` |
| `Sidecar.Memory` + `Sidecar.Tools.UpdateMemory` | Per-agent short-term memory — a `Planck.Agent.Hooks.Prompt` implementation backed by an ETS cache (warmed lazily on `:turn_end`, refreshed eagerly on `:compacted`) over the `short_term_memory` Typesense collection; `update_memory` tool enforces a 2,200-char limit | `specs/sidecar.md` (hook mechanism), `specs/bundled-sidecar-tools.md` (tool) |
| `Sidecar.SessionIndexer` + `Sidecar.Tools.SessionSearch` | Long-term memory — every turn is indexed into the `long_term_memory` Typesense collection; `session_search` tool queries it | `specs/bundled-sidecar-tools.md` |
| `Sidecar.SkillReflector` | A `Planck.Agent.Hooks.TurnEnd` implementation — spawns an ephemeral mini-agent to capture a reusable skill once a turn's tool-call count crosses a threshold | `specs/sidecar.md` |
| `Sidecar.Beads` + `bd_*` tools + `Sidecar.Widgets.Beads` | Shared task tracking — HTTP client, seven LLM-facing tools, and a live kanban board widget rendered in the chat UI | `specs/bundled-sidecar-tools.md` |
| `Sidecar.Secrets.AgentVault` | `Planck.Agent.Secrets` implementation — see "Credential proxy" above | this file |
| `Sidecar.Typesense` | Shared HTTP client used by `Watcher`/`Memory`/`SessionIndexer`/`SessionSearch` (`get/2`, `upsert/2`, `delete/2`, `search/2`, `ensure_collection/1`) | — |
| `Sidecar.Gettext` | Sidecar's own Gettext backend (`en`/`es`) — sidecar-rendered widgets (the beads board) translate through this, since the sidecar is a separate distributed-Erlang node and can't share a Gettext process with `planck_cli` | — |
| `Sidecar.FileType` | Content-sniffing binary/text classifier (UTF-8 validity sampling, no extension allowlist) used by `Read` and `Watcher` | — |
| `Sidecar.Reloader` | `:dev`-only code-reload convenience, not present in the shipped image's `:prod`/`:test` supervision tree | — |

## Bundled skills

### `configure-searxng`

Tells agents where `settings.yml` lives inside the container and documents
the key settings (engines, language, safe search, result count). Agents use
`read`/`edit` to apply changes. Always reminds the user that
**`docker compose restart`** is required for changes to take effect.

## Default config

No default config is written. On first launch Planck shows a SetupModal
where the user selects a provider and enters their API key. The resulting
`config.json` is then written to the workspace by the UI.

## Install script

`docs/install_docker.sh` — follows the same structure as `docs/install.sh`:

```sh
curl -fsSL https://thebroken.link/planck/install_docker.sh | sh
```

Options:

| Flag | Default | Description |
|---|---|---|
| `--bind` | `127.0.0.1` | Address to bind planck on the host |

Examples:

```bash
# Local only (default — safe for a non-technical user's machine)
curl -fsSL .../install_docker.sh | sh

# Expose on network (server deployment)
curl -fsSL .../install_docker.sh | sh -s -- --bind 0.0.0.0
```

The script is idempotent — all write steps use an `add_if_missing` pattern so
existing files and `.env` keys are never overwritten. The script:

1. Checks Docker is installed and running; exits with install instructions if not
2. Pulls all Docker images (and builds the locally-built `dolt`/`beads` images)
3. Creates `$HOME/planck/{typesense-data,vault-data,dolt-data,beads-data}`
4. Writes `$HOME/planck/.env` with `PLANCK_BIND_ADDRESS`, `TYPESENSE_API_KEY`,
   `SEARXNG_SECRET`, `AGENT_VAULT_MASTER_PASSWORD`, `AGENT_VAULT_EMAIL`,
   `AGENT_VAULT_PASSWORD`, and `BEADS_TOKEN` (skips keys already present)
5. Copies bundled sidecar to workspace (skips if present)
6. Starts all services: `docker compose up -d`

## Updates

```sh
curl -fsSL https://thebroken.link/planck/install_docker.sh | sh
```

Re-running the install script is safe — it skips steps already completed
and pulls/rebuilds updated Docker images.

## System requirements

- Docker installed and running
- 4 GB RAM
- 2 GB disk (Docker images)

Seven services now run concurrently (`planck`, `searxng`, `typesense`,
`tika`, `vault`, `dolt`, `beads`) versus the original three — these numbers
predate that growth and haven't been re-measured against the current stack.

## Docker images released per version

| Image | Source |
|---|---|
| `ghcr.io/alexdesousa/planck:VERSION` | This repo — Elixir + Node.js + sidecar |

`dolt` and `beads` are **not** published per-version images — they're built
locally from `planck_docker/dolt/Dockerfile` and `planck_docker/beads/Dockerfile`
on install/update. `dolt`'s base image is pinned below `2.3.0` (`2.3.0`/`2.3.1`
regressed `DOLT_RESET('--hard')`; later patch releases don't confirm a fix).
`searxng`/`typesense`/`tika`/`vault` are pulled from their own upstream
registries at the versions pinned in `compose.yml`.
