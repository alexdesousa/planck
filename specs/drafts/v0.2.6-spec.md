# Planck v0.2.6 — Spec

## Scope

Adds two user-facing capabilities to the skills system:

1. **`disable-model-invocation` frontmatter** — a boolean SKILL.md frontmatter
   field that, when `true`, removes a skill from the set the model can load on
   its own (via `load_skill` / the system-prompt index), while keeping it in
   `ResourceStore` so the UI can still surface and dispatch it.

2. **Slash-command skills** — typing `/skill-name` (optionally followed by
   extra user instructions) at the start of a chat message loads the named
   skill into the agent's context as a synthetic `load_skill` tool-call /
   tool-result pair, then passes the user's text as a normal user message.
   The UI surfaces this with an autocomplete dropdown triggered by a leading
   `/`, showing every skill in the store (with disabled-invocation skills
   visually marked), selectable by mouse or ↑/↓ arrow keys.

In scope:

- A `disable_model_invocation` field on `Planck.Agent.Skill.t()` and its
  frontmatter parser.
- Filtering that field out of the agent-facing skill pool at the three wiring
  points in `planck_headless`.
- Preservation of the field by the sidecar's `write_skill` tool.
- A backend path that parses `/skill-name [extra]` at the start of a prompt,
  reads the skill from `ResourceStore`, and injects a synthetic `load_skill`
  tool-call + tool-result into the session before the user's message.
- A UI dropdown rendered by `PromptInput` when the textarea text starts with
  `/`, with keyboard (↑/↓/Enter/Esc) and mouse selection.

## Objective

Give users explicit, predictable control over which skills an agent
self-loads, while providing a fast keyboard-driven way to force-load any
skill — including ones the model is no longer allowed to invoke on its own.
The two features are complementary: `disable-model-invocation` removes a
skill from the model's autonomous reach, and slash commands give the user a
way to bring it back on demand without editing config.

## Use Cases

- A skill whose instructions are expensive to follow (long, multi-step) is
  marked `disable-model-invocation: true` so the model doesn't pull it in
  speculatively on every vaguely-related turn; the user types `/heavy-skill`
  when they actually want it run.
- A skill the user wants to gate behind explicit intent (destructive cleanup,
  billing actions) is disabled for model invocation and only ever loaded by a
  deliberate `/billing` keystroke — the model can't decide on its own to load
  it.
- A user mid-conversation types `/grill-me give me five hard follow-up
  questions` — the dropdown filters to matching skills as they type, they
  arrow-select `grill-me`, the skill loads as a synthetic tool call, and the
  agent receives both the skill content and the appended extra instruction.
- A user discovers available skills by typing `/` alone and browsing the
  dropdown, including skills the model can already self-load (shown unmarked)
  and disabled ones (shown with a badge).

## Explicitly not touched

- **Renaming or removing the `skills` array in TEAM.json.** It's carried
  through `AgentSpec.skills` → `SkillIndex.names` but is not currently
  enforced at runtime (see the `skills.md` spec note). This spec doesn't
  change that — it adds an orthogonal, enforced filter (`disable_model_invocation`)
  rather than fixing the dormant one. Revisit the TEAM.json `skills` filter
  separately if/when desired.
- **Slash commands for non-skill actions** (e.g. `/reset`, `/model`). Only
  skill loading is in scope. A general command registry could be a follow-up.
- **Mid-message slash commands.** Per the user's decision, `/skill-name`
  only triggers at the start of the message. Inline parsing is out of scope.
- **Persisting slash-command usage into `SkillUsage` (`.planck/skills.db`).**
  The synthetic tool call reuses the existing `on_use` callback path, so
  usage *is* recorded the same way a real `load_skill` call records it —
  but no new persistence shape is introduced.
- **The `list_skills` tool.** Still opt-in via TEAM.json, still reflects the
  filtered (post-Step-2) pool. No change.

## Open questions (must resolve before/during implementation)

1. **Synthetic tool-call injection API.** Step 4 needs a way to insert an
   assistant `tool_calls` message + a `tool`-role result message into a
   `Session` before the user's text is processed. Investigate
   `Planck.Agent.Session`'s insertion API during Step 4's TDD pre-work — if
   no clean insertion point exists, fall back to injecting the skill content
   as a system-message preamble (simpler, but diverges from the user-chosen
   "tool-call simulation" approach and should be called out in that step's
   file if it happens).
2. **Whether disabled-invocation skills should still be reachable by
   `spawn_agent`'s `filter_granted`.** Current plan: yes — the filter in
   Step 2 only touches the static-agent wiring points, not the dynamic
   `spawn_agent` path (`tools.ex:283`), which intersects by name against the
   *full* `store.skills` pool. Confirm during Step 2; if the intent is that
   disabled skills are also hidden from orchestrator-granting, extend the
   filter there too. Left open because `spawn_agent` already requires the
   orchestrator to name skills explicitly, which is closer to "user-driven"
   than "model-autonomous".
3. **Dropdown positioning when the textarea is at the bottom of a scrolling
   chat.** The existing `FloatingDropdown` hook repositions *below* its
   trigger. A skill dropdown likely needs to open *above* the textarea.
   Resolve during Step 6 with a `position: :above` option or a separate hook.
