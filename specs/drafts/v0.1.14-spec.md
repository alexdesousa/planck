# Planck v0.1.14 — Spec

## Overview

Two related capabilities that let a sidecar put real UI in front of the user, instead of being limited to plain-text tool results:

1. **Sidecar widgets** — a sidecar can render its own markup (real Phoenix Components/HEEx) and stream it into the main WebUI, with live updates pushed back over PubSub and user actions dispatched back to the sidecar over RPC.
2. **`{:custom, :ui}` messages** — a tool call can attach a UI-only side effect (e.g. "here's a button that opens a widget") to the chat transcript without that side effect ever reaching the LLM's context.

Both were designed against a concrete motivating case — integrating [beads](https://github.com/gastownhall/beads), a task/issue tracker for coding agents, as a sidecar tool with a visual kanban board — and **that integration is this version's deliverable**, not deferred follow-up work. Earlier drafts of this spec planned `write_skill` as the proof of concept instead, since it needed only Section 2; that was dropped because `write_skill` only fires when an LLM decides to call it (or via the `SkillReflector`'s async mini-agent loop), which makes it awkward to trigger deterministically in a test. `bd` is a plain CLI — a `bd_ready`-style tool can be exercised directly, end to end, without depending on model behavior at all. It's more work (it needs both sections, not just Section 2), but it's the better validation target.

### Explicitly not touched

- **Credentials / `SetupModal`** — during design it was tempting to move the agent-vault credential UI onto this same widget mechanism. Rejected: `Planck.Headless.Secrets` already dispatches transparently between `EnvFile` (standalone) and `Sidecar.Secrets.AgentVault` (Docker) via `:rpc.call/5`, so `SetupModal.KeysStep` is already one code path for both backends. Introducing widget-streaming there would split one maintained implementation into two. Leave as-is.
- **Third-party/MCP-registered widgets** — this spec assumes the sidecar shipping markup is first-party and bundled by Planck (same trust level as `planck_agent` itself). If a future `connect_mcp(url)` mechanism lets an arbitrary external MCP server register a widget, shipping raw HTML from it becomes an XSS vector, and that path needs a data-only/fixed-catalog renderer instead of what's described here.

---

## 1. Sidecar Widgets

### Problem

A sidecar tool's only current output is plain text in a tool-result bubble (`Planck.Agent.Sidecar.execute_tool/4` → a string). For sidecar-owned state that's inherently visual or long-lived (a task board, a dependency graph, a live log), there's no way to show anything beyond that text, and no existing abstraction to build on the way `Planck.Agent.Secrets` already covers credentials.

### Design decisions

- **The sidecar ships markup, not just data.** A widget module is allowed to use `Phoenix.Component`/HEEx to build its own UI. This is the point of the feature — new widget *kinds* don't require a `planck_cli` release.
- **Never send `%Phoenix.LiveView.Rendered{}` (or any closures) across the RPC boundary.** It embeds anonymous functions for diff-tracking; funs sent between distributed Erlang nodes only execute correctly if the receiving node has byte-identical compiled code for that module, which defeats independent sidecar versioning. Instead, the sidecar flattens its own render to a plain HTML string (`Phoenix.HTML.Safe.to_iodata/1` → `IO.iodata_to_binary/1`) before the RPC call returns. Only ever a `binary()` crosses the wire.
- **Pull for the initial paint, push for updates.** Opening a widget does one RPC call for a first snapshot; after that, the sidecar broadcasts fresh HTML over `Phoenix.PubSub` whenever its underlying state changes. This mirrors the already-proven pattern in `sidecar/lib/sidecar/session_indexer.ex`, which already subscribes to a topic on `Planck.Agent.PubSub` from the sidecar node — cross-node PubSub on a shared topic name is existing, working infrastructure, not new.
- **Actions round-trip through the same broadcast, not a synchronous reply.** Clicking a button in a widget dispatches an RPC call to the sidecar; the sidecar mutates its own state and then broadcasts the refreshed HTML on the widget's topic. Every open viewer (including the one that clicked) updates from that broadcast. No special-casing "my own click."
- **`phx-target` needs the LiveComponent's CID baked in.** The sidecar's render call has no socket/component context, so `JS.push(..., target: @myself)` can't resolve `@myself` on the sidecar side. The CID is passed in as a plain argument and rendered into the HTML as a literal `phx-target` attribute value.
- **`Tool` and `Widget` stay separate behaviours — but widget discovery is derived from `tools/0`, not a second declared list.** `Planck.Agent.Widget` keeps its own identity (a widget is not a tool: different return shape and different dispatch path, see below). What's removed is the *second, independent* `widgets/0` callback: `Planck.Agent.Tool.t()` gains an optional `:widget` field holding the *module* that implements `Planck.Agent.Widget`, and `list_widgets/0` filters `tools/0` for tools that have one. One thing to declare per pairing, not two.
- **Declaration is derived; dispatch still isn't shared with `execute_tool/4`.** A widget's render/action calls do not reuse the LLM tool-execution path, for two concrete reasons: (1) `execute_tool/4` results flow into `finish_tool_execution/2`, which appends to the agent's actual message history sent back to the LLM — a human clicking a widget button has no corresponding assistant-issued `tool_call`, and faking one to satisfy that invariant is worse than just having separate RPC entry points; (2) `execute_fn`'s contract (`{:ok, string} | {:error, string}`) is meant for the model's context, while a widget's output is meant for a UI surface to render — a different kind of value entirely.
- **A widget declares its own container type — optionally, via `use`.** `Planck.Agent.Widget` gains an *optional* `container/0` callback (`@optional_callbacks container: 0`) returning `:modal | :drawer | :fullscreen`. `use Planck.Agent.Widget` (instead of a bare `@behaviour Planck.Agent.Widget`) injects `@behaviour` plus a default `container/0` returning `:modal`, `defoverridable` for widgets that want something else once a second container kind exists. This is a real injected function, not a caller-side default: an earlier version of this design had `Planck.Agent.Sidecar.widget_container/1` fall back to `:modal` via `function_exported?/3` when the widget didn't implement `container/0`, so a direct call to a bare-behaviour widget's `container/0` would raise while the RPC path silently returned `:modal` — two different answers depending on how you asked. Rejected in favor of the macro precisely so both paths agree: calling `container/0` directly behaves identically to calling it through `widget_container/1`. The cost: a widget written with a bare `@behaviour` (no `use`) gets no default at all — that's an accepted, deliberate tradeoff, not an oversight.
- **`planck_agent` does not know its widgets produce HTML.** `Planck.Agent.Widget` and `Planck.Agent.Sidecar` live in `planck_agent`, which is UI-agnostic today (its only Phoenix-adjacent dependency is `phoenix_pubsub`; no `phoenix_live_view`/`Phoenix.Component`). The behaviour's render callback returns an **opaque `term()`** — `planck_agent` never inspects or interprets it, only RPCs it through. `planck_cli` is the one place that assumes the term is an HTML string and does `raw/1` on it; the sidecar module is the one place that chooses to `use Phoenix.Component` to build one. This was weighed against making the contract carry structured *data* instead of markup (fully renderer-portable, but reintroduces "new widget kind needs a `planck_cli` release" — the exact cost the "sidecar ships its own markup" decision above was meant to avoid) and rejected for now: `planck_tui` doesn't exist yet, so there's no second UI surface to design portability against. If one shows up, a widget module written for `planck_cli` won't automatically work there — a `planck_tui`-targeting widget would need its own separate module producing whatever `planck_tui` expects, reusing the same `Planck.Agent.Widget` behaviour and the same `:widget` field on `Tool`, just with a different implementation. Revisit if and when that becomes real instead of hypothetical.

### `Planck.Agent.Tool` — new optional field

### `Planck.Agent.Sidecar` — `list_widgets/0` derived from `tools/0`, no separate callback

```elixir
# planck_agent/lib/planck/agent/sidecar.ex — no new @callback
def list_widgets, do: discover() |> apply(:tools, []) |> Enum.filter(& &1.widget) |> Enum.map(& &1.widget)
def widget_render(widget_id, myself), do: fetch_widget!(widget_id).render(myself)
def widget_action(widget_id, action, args), do: fetch_widget!(widget_id).handle_action(action, args)
def widget_container(widget_id), do: fetch_widget!(widget_id).container()
```

`Planck.Agent.Widget` behaviour — `render/1`'s return value is opaque to `planck_agent`, `container/0` is optional and macro-provided:

```elixir
@callback id() :: String.t()
@callback render(myself :: term()) :: term()   # opaque — planck_agent never inspects this
@callback handle_action(action :: String.t(), args :: map()) :: :ok | {:error, term()}
@callback container() :: :modal | :drawer | :fullscreen   # optional
@optional_callbacks container: 0

defmacro __using__(_options) do
  quote do
    @behaviour Planck.Agent.Widget
    @impl Planck.Agent.Widget
    def container, do: :modal
    defoverridable container: 0
  end
end
```

Widgets use `use Planck.Agent.Widget`, not a bare `@behaviour Planck.Agent.Widget`, to get the default — `widget_container/1` above calls `.container()` directly with no `function_exported?/3` fallback, so a bare-`@behaviour` widget that skips implementing `container/0` raises there too, consistently with a direct call.

### Beads tool + widget (the deliverable)

```elixir
# planck_docker/sidecar/lib/sidecar/tools/beads_ready.ex — the tool
defmodule Sidecar.Tools.BeadsReady do
  def tool do
    Planck.Agent.Tool.new(
      name: "bd_ready",
      description: "List beads with no open blockers.",
      parameters: %{"type" => "object", "properties" => %{}},
      execute_fn: fn _agent_id, _id, _args ->
        # format_ready_beads/0 wraps Sidecar.Beads.ready/1 (GET /v0/beads/ready)
        # and formats the {:ok, %{"items" => [...]}} result as text for the model.
        {:ok, format_ready_beads(),
         %{ui: %{kind: :widget, label: "View kanban board", widget: "beads-board", data: nil}}}
      end,
      widget: Sidecar.Widgets.Beads
    )
  end
end
```

`data` is `nil` here rather than a real snapshot — the widget pulls its own first paint via `Planck.Agent.Widget.render/1` when opened (Section 1's pull-then-push model), so there's no need to duplicate the same data into the tool result too. Contrast with the earlier `write_skill` sketch, where `data` carried the *entire* payload because there was no RPC pull step at all.

This sketch predates several corrections landed while actually building it — see "Beads tool set (LLM-facing)" below for the real `description` phrasing ("Use when...", not "List..." — a situational trigger for the LLM, not a mechanical summary) and the final tool set (seven, not one), and "`Sidecar.Beads` — HTTP client" below for the `tool/1` (not `tool/0`) signature every beads tool ended up with, and why.

**Done — two real bugs found in the sketch above before it was ever built, both caught by verification rather than by testing after the fact:**

1. **`fetch_beads/0`'s own comment names `Sidecar.Beads.list(status: ["open", "in_progress"])`, and that call crashes.** Confirmed via `mix run`: `Req`'s `params:` option calls `URI.encode_query/1` directly, which raises `ArgumentError` outright on a list-valued entry — there's no list-flattening. The OpenAPI spec documents a comma-separated string as an equally valid alternative encoding to repeating the parameter (`style: form, explode: true`, and the `status` parameter's own description explicitly names both forms), so the real call is `Sidecar.Beads.list(status: "open,in_progress")` — a string, not a list.
2. **The claim control's `phx-click` only ever sends `args: %{id: bead["id"]}}`, but `handle_action("claim", %{"id" => id, "assignee" => assignee})` requires an `assignee` that nothing in the sketch collects.** The original design assumed a live "who's claiming this" picker (see below); the gap wasn't visible until actually wiring the click handler to the declared `handle_action/2` clause.

The actual widget, with both fixed:

```elixir
# planck_docker/sidecar/lib/sidecar/widgets/beads.ex — the widget (done)
defmodule Sidecar.Widgets.Beads do
  use Phoenix.Component   # this module's choice — planck_agent doesn't require or know about it
  use Planck.Agent.Widget # not a bare @behaviour — see Section 1's "container/0" design decision;
                          # injects @behaviour + a default container/0 returning :modal

  @column_order ["open", "in_progress"]

  def id, do: "beads-board"

  # render/1 — the actual Planck.Agent.Widget callback, the only arity real
  # dispatch ever calls — is a thin wrapper over render/2. render/2 exists
  # solely so Sidecar.Beads.broadcast_refresh/1 (below) can re-render against
  # an injected test client without the *callback* itself gaining a second
  # argument every widget kind would have to carry.
  def render(myself), do: render(myself, [])

  def render(myself, opts) do
    assigns = %{columns: fetch_columns(opts), myself: myself}

    ~H"""
    <form phx-submit="widget_action" phx-target={@myself}>
      <input type="hidden" name="action" value="create" />
      <input type="hidden" name="args[actor]" value="human" />
      <input type="text" name="args[title]" placeholder="Title" required />
      <button type="submit">Create</button>
    </form>

    <div class="grid grid-cols-2 gap-3">
      <div :for={{status, beads} <- @columns}>
        <p>{status}</p>
        <div :for={bead <- beads}>
          <p>{bead["id"]}: {bead["title"]}</p>
          <form phx-submit="widget_action" phx-target={@myself}>
            <input type="hidden" name="action" value="claim" />
            <input type="hidden" name="args[id]" value={bead["id"]} />
            <input type="text" name="args[assignee]" placeholder="assignee" required />
            <button type="submit">Claim</button>
          </form>
          <button phx-click={JS.push("widget_action", value: %{action: "done", args: %{id: bead["id"], actor: "human"}}, target: @myself)}>Done</button>
          <button phx-click={JS.push("widget_action", value: %{action: "delete", args: %{id: bead["id"], actor: "human"}}, target: @myself)}>Delete</button>
        </div>
      </div>
    </div>
    """
    |> Phoenix.HTML.Safe.to_iodata()
    |> IO.iodata_to_binary()
  end

  def handle_action("claim", %{"id" => id, "assignee" => assignee}) do
    with {:ok, _} <- Sidecar.Beads.claim(id, assignee) do
      Sidecar.Beads.broadcast_refresh()
      :ok
    end
  end

  def handle_action("create", %{"title" => title, "actor" => actor}) do
    with {:ok, _} <- Sidecar.Beads.create(title, actor), do: (Sidecar.Beads.broadcast_refresh(); :ok)
  end

  def handle_action("delete", %{"id" => id, "actor" => actor}) do
    with {:ok, _} <- Sidecar.Beads.delete([id], actor), do: (Sidecar.Beads.broadcast_refresh(); :ok)
  end

  def handle_action("done", %{"id" => id, "actor" => actor}) do
    with {:ok, _} <- Sidecar.Beads.close(id, actor), do: (Sidecar.Beads.broadcast_refresh(); :ok)
  end

  defp fetch_columns(opts) do
    list_opts = [status: "open,in_progress"] ++ Keyword.take(opts, [:client])

    case Sidecar.Beads.list(list_opts) do
      {:ok, %{"items" => items}} ->
        by_status = Enum.group_by(items, & &1["status"])
        Enum.map(@column_order, &{&1, Map.get(by_status, &1, [])})

      {:error, _reason} ->
        Enum.map(@column_order, &{&1, []})
    end
  end
end
```

**The assignee field is a plain text input, not a live picker — a deliberate descope, not a shortcut taken silently.** The original design (see the now-corrected "Agent picker for 'assign to'" note below) called for sourcing it from the live agent registry. But `render/2` executes on the **sidecar node**, and `Planck.Agent.Registry`/every running `Planck.Agent` process live on the **`planck_headless` node** — a `Registry` is per-node, so a local lookup from the sidecar would find nothing. A live picker needs cross-node RPC infrastructure that doesn't exist today (the existing `Planck.Headless.Widgets`/`Planck.Headless.Secrets` RPC modules go the other direction — headless calling *into* the sidecar, not the reverse). Free text for this pass; wiring an actual picker is real, but separate, follow-up work. The create form has the same limitation for a different reason: it only collects a title, not `bd_create`'s optional `description`/`priority`, purely because this pass didn't build those two fields into the form — nothing structural blocks adding them later.

**`fetch_columns/2` gracefully degrades to two empty columns on any fetch error** (network failure, beads unreachable, ...) rather than crashing the render — matters most for `broadcast_refresh/1` below, whose whole point is a best-effort background refresh, not a request a human is waiting on.

### `Sidecar.Beads` — HTTP client (done)

Not an `:exec.run` wrapper — see "Beads as dedicated Docker services" below for why. `Sidecar.Beads` is a `Req`-based HTTP client, the same pattern already used for Typesense/Searxng/Tika/agent-vault (`Sidecar.Typesense`, `sidecar/lib/sidecar/secrets/agent_vault.ex`), talking to the `beads` compose service over the internal Docker network. Matches `Sidecar.Typesense`'s exact style once actually written — `Req.get/2`/`Req.post/2` with explicit `headers:`/`json:` opts, not the generic `Req.request/1` an earlier version of this sketch used, and `url/2`/`headers/1` private (nothing outside the module needs them).

Verified against `internal/httpapi/spec/openapi.v0.yaml` in the beads repo source (not served over HTTP — `bd serve --help`'s "(/v0)" refers to the API version, not a fetchable URL; the CLI's own `--help` output describes the CLI, not this contract). Every shape below is read from that file, not guessed:

```elixir
# planck_docker/sidecar/lib/sidecar/beads.ex
defmodule Sidecar.Beads do
  @type client :: %{url: String.t(), token: String.t()}

  # GET /v0/beads/issues — status/limit/cursor/sort/all as query params.
  # Default excludes closed status; pass status: "closed" for the done list,
  # or all: true for every status at once (what bd_list, Phase 14, uses).
  # For the widget's board (open + in_progress columns) and bd_list's
  # overview, not for bd_ready — see ready/1, a different endpoint with
  # different semantics.
  @spec list(keyword()) :: {:ok, map()} | {:error, term()}
  def list(params \\ []) do
    {client, query} = extract_client(params)
    get(client, "/v0/beads/issues", query)
  end

  # GET /v0/beads/ready — a DIFFERENT endpoint from list/1 with status
  # filtering, not a parameter on it. Restricted to status=open AND no
  # unresolved blockers — an open-but-blocked issue would pass a naive
  # status=open filter on list/1 but never appears here. This is what
  # bd_ready (the LLM tool) calls, matching bd ready --json exactly.
  @spec ready(keyword()) :: {:ok, map()} | {:error, term()}
  def ready(params \\ []) do
    {client, query} = extract_client(params)
    get(client, "/v0/beads/ready", query)
  end

  # GET /v0/beads/issues/{id} — the single-issue read, not a list filter.
  # Added mid-implementation for bd_get: an agent that claimed a bead has no
  # other way to notice a human-edited description since — ready/1 no
  # longer lists it once claimed, and claim/2's own response is a one-time
  # snapshot from claim time.
  @spec fetch(String.t(), keyword()) :: {:ok, map()} | {:error, term()}
  def fetch(id, opts \\ []) do
    {client, _opts} = extract_client(opts)
    get(client, "/v0/beads/issues/#{id}", [])
  end

  # POST /v0/beads/issues — CreateIssueRequest: required [actor, title].
  # issue_type is technically optional in the schema but an omitted one is
  # refused by workspace validation on every shipped workspace — this is
  # exactly what tripped the unexplained 400 seen while testing. Always send it.
  # opts[:description]/opts[:priority] are included only when given — an
  # absent member means "workspace default", not the same as an explicit
  # null (some CreateIssueRequest fields are documented as refusing null
  # outright as a redundant spelling of omission).
  @spec create(String.t(), String.t(), keyword()) :: {:ok, map()} | {:error, term()}
  def create(title, actor, opts \\ []) do
    {client, opts} = extract_client(opts)

    body =
      %{title: title, actor: actor, issue_type: "task"}
      |> maybe_put(:description, opts[:description])
      |> maybe_put(:priority, opts[:priority])

    post(client, "/v0/beads/issues", body)
  end

  # POST /v0/beads/issues/{id}:claim — ClaimRequest: {actor} ONLY.
  # additionalProperties: false, so a redundant "assignee" field (an earlier
  # draft of this sketch included one) would be refused outright as an
  # unknown body member. Real compare-and-set semantics server-side: 200
  # {already_claimed: true} on an idempotent re-claim by the same actor,
  # 409 {already_claimed, assignee: <holder>} if someone else holds it,
  # 409 {not_claimable, issue_status: ...} if it's not in a claimable state.
  # No client-side race guard needed — the server already does this properly.
  @spec claim(String.t(), String.t(), keyword()) :: {:ok, map()} | {:error, term()}
  def claim(id, actor, opts \\ []) do
    {client, _opts} = extract_client(opts)
    post(client, "/v0/beads/issues/#{id}:claim", %{actor: actor})
  end

  # POST /v0/beads/issues/{id}:close — CloseIssueRequest: required [actor],
  # optional reason/session/force/expected_version. Idempotent re-close
  # (200, already_closed: true) writes neither reason nor session — first
  # close wins. opts[:reason] replaces what used to be a positional 3rd arg —
  # folded into opts once opts existed anyway for :client, rather than
  # carrying both a positional reason and a trailing opts list.
  @spec close(String.t(), String.t(), keyword()) :: {:ok, map()} | {:error, term()}
  def close(id, actor, opts \\ []) do
    {client, opts} = extract_client(opts)
    post(client, "/v0/beads/issues/#{id}:close", %{actor: actor, reason: opts[:reason]})
  end

  # POST /v0/beads/issues:delete — a collection-level custom method, NOT
  # DELETE /v0/beads/issues/{id} (an earlier draft of this sketch guessed
  # wrong). DeleteIssuesRequest: required [ids] (array, 1-1000), actor
  # optional. Refuses (400) if a named bead has a dependent outside the
  # request unless cascade/force is set — not needed for our single-id case.
  @spec delete([String.t()], String.t() | nil, keyword()) :: {:ok, map()} | {:error, term()}
  def delete(ids, actor \\ nil, opts \\ []) when is_list(ids) do
    {client, _opts} = extract_client(opts)
    post(client, "/v0/beads/issues:delete", %{ids: ids, actor: actor})
  end

  # Tells every open beads board widget to re-render — called by every
  # mutating tool below and by the widget's own handle_action/2, after their
  # write succeeds. Renders through Sidecar.Widgets.Beads's render/2 (not the
  # render/1 callback — see that module above), forwarding opts so :client
  # reaches the board's own re-fetch too, not just whichever write triggered
  # this call. :instance overrides the topic's widget id (default
  # "beads-board", matching the widget's own id/0) — only a test asserting on
  # several of these concurrently needs it, to give each one a topic the
  # others can't land a message on; real dispatch never sets it.
  @spec broadcast_refresh(keyword()) :: :ok | {:error, term()}
  def broadcast_refresh(opts \\ []) do
    {instance, render_opts} = Keyword.pop(opts, :instance, "beads-board")

    Phoenix.PubSub.broadcast(
      Planck.Agent.PubSub,
      "sidecar:widget:#{instance}",
      {:widget_rendered, instance, Sidecar.Widgets.Beads.render(nil, render_opts)}
    )
  end

  # ---------------------------------------------------------------------------
  # Private — matches Sidecar.Typesense's Req.get/2 + Req.post/2 style, not a
  # generic Req.request/1 wrapper.

  # Every function above reads Sidecar.Config's beads_url!/beads_token! by
  # default; passing client: %{url:, token:} in its opts/params overrides
  # both for that one call, without touching Sidecar.Config (and so without
  # the global Application.env mutation that would force a test using it to
  # run async: false). Exists for tests only — a real deployment has exactly
  # one beads instance and no reason to override it per call.
  defp extract_client(opts) do
    case Keyword.pop(opts, :client, nil) do
      {nil, rest} -> {default_client(), rest}
      {client, rest} -> {client, rest}
    end
  end

  defp default_client, do: %{url: Sidecar.Config.beads_url!(), token: Sidecar.Config.beads_token!()}

  defp get(client, path, params), do: respond(Req.get(url(client, path), headers: headers(client), params: params))
  defp post(client, path, body), do: respond(Req.post(url(client, path), headers: headers(client), json: body))

  defp respond({:ok, %{status: s, body: body}}) when s in 200..299, do: {:ok, body}
  defp respond({:ok, %{status: s, body: body}}), do: {:error, {s, body}}
  defp respond({:error, reason}), do: {:error, reason}

  defp url(client, path), do: client.url <> path
  defp headers(client), do: [{"authorization", "Bearer #{client.token}"}]
end
```

Every one of the six LLM-facing tools (see "Beads tool set" below) gained a matching `tool/1` (not `tool/0`) signature purely to carry this same `opts` down to its own `Sidecar.Beads` call and, for the four mutating ones, into `broadcast_refresh/1` too — `Sidecar.Planck.tools/0` still calls each with zero args (the default), so this is invisible to real dispatch and exists only so a test can inject a `:client`/`:instance` without any `Application.put_env`/`Config.reload_*` dance. That, in turn, is what let the read-only tools' (`bd_ready`/`bd_get`/`bd_list`) test files drop `async: false` entirely.

**One beads instance per Planck installation, shared by every agent and session** — not per-project, not per-session. Tasks here are meant as a structured way to hand work to workers (in place of a prompt), typically thrown away once done, not a long-lived per-project backlog — so there's no "which project does this session belong to" scoping to design.

### `Sidecar.Config` — new `beads_url` key

### Beads tool set (LLM-facing)

**Done — seven separate tools, not one tool with an action parameter** — deliberate, so `TEAM.json`'s existing per-member `"tools"` list (see `AgentSpec.resolve_tools/2`, `planck_agent/lib/planck/agent/agent_spec.ex:265-278`) can restrict them individually. `bd_get` was added mid-implementation, beyond the five originally planned; `bd_list` was added later still, alongside Phase 14 — see below for both.

| Tool | `Sidecar.Beads` call | Scope | Attaches board `ui:`? |
|---|---|---|---|
| `bd_ready` | `ready(opts)` — dedicated endpoint, not a `list/1` filter | workers opt in via `TEAM.json` | yes |
| `bd_get` | `fetch(id, opts)` — single-issue read by exact id | workers opt in via `TEAM.json` | yes |
| `bd_list` | `list([all: true] ++ opts)` — every status, grouped, not just ready/unblocked | orchestrator (see below) | yes |
| `bd_done` | `close(id, actor, opts)` | workers opt in via `TEAM.json` | yes |
| `bd_claim` | `claim(id, "<resolved id>", opts)` | orchestrator (see below) | yes |
| `bd_create` | `create(title, actor, [description:, priority:] ++ opts)` | orchestrator (see below) | yes |
| `bd_delete` | `delete([id], actor, opts)` | orchestrator (see below) | yes |

Each tool's `opts` here is the same test-only `:client`/`:instance` mechanism described under "`Sidecar.Beads` — HTTP client" above — `tool/1`, not `tool/0`; every real dispatch call omits it.

**`bd_list` fills a gap the other six don't cover: a whole-board overview, not just what's unblocked.** Added after a review of Phase 14's work, not part of the original five-or-six-tool plan — `bd_ready` deliberately excludes anything already claimed or blocked, which is exactly what an orchestrator checking "what's done, what's in progress, what's still pending" needs to see. Calls `Sidecar.Beads.list/1` with `all: true` (the one call this whole design needed that flag for) — `list/1`'s own default silently excludes closed and other done/frozen statuses, which is the one thing an overview must not do. Orchestrator-only, matching `bd_claim`/`bd_create`/`bd_delete`: seeing the whole board (including finished work) is an orchestration concern, not a per-worker one.

**Every tool attaches the board-opening `ui:` payload on success, not just `bd_ready`.** The original plan only put it on `bd_ready`, reasoning it was the "entry point" — but a turn that only claims, creates, marks done, deletes, lists, or re-fetches (never calling `bd_ready` in that same turn) would otherwise leave the human with no way to open the board from that turn at all. `Sidecar.Tools.Beads.board_ui/0` is the single shared source for the payload (`%{kind: :widget, label: "View kanban board", widget: "beads-board", data: nil}`), so every tool stays in sync by construction rather than by remembering to copy a literal into each file.

**`bd_get` fills a real gap the other five leave open.** An agent claims a bead, sees its description once (from `bd_claim`'s response), then works on it for a while — if a human edits that description in the widget meanwhile, nothing tells the agent. `bd_ready` stops listing a bead once it's claimed (no longer "ready"), and `bd_claim`'s response is a one-time snapshot from claim time, not a standing view. `bd_get` (`GET /v0/beads/issues/{id}`, confirmed in the OpenAPI spec — a genuine single-issue read, not a list filter) is worker-scoped like `bd_ready`/`bd_done`: checking your own claimed work's current state isn't an orchestration decision.

**`bd_ready`/`bd_get` surface each issue's `description`, not just title/type/priority** — an earlier version of both tools' formatting dropped it, even though `IssueWithCounts`/`Issue` both carry it. An agent judging what to claim, or re-checking what it's already claimed, needs more than a title to go on. `bd_claim`'s success message does the same from `ClaimResponse.issue.description` — that response carries the full issue, not just a confirmation flag, so a second round-trip isn't needed right after claiming.

**No new `planck_agent` code needed for permissions.** `AgentSpec.resolve_tools/2` already resolves an empty `spec.tools` (the common case for an orchestrator, which doesn't normally declare a restrictive list) to the *entire* tool pool — so as long as all six tools are registered sidecar tools, the orchestrator gets all of them automatically, in any team shape (static or dynamic), with no config or code change. Workers only get `bd_ready`/`bd_get`/`bd_done` if they explicitly list those names in their own `TEAM.json` `"tools"` array.

**`bd_claim`'s identity resolution** — the LLM never supplies who's claiming; the tool resolves it server-side from the runtime-provided `agent_id`, the same way `Sidecar.Tools.UpdateMemory.resolve_agent_info/1` already does, since `agent_id` itself is `:crypto.strong_rand_bytes(8)` regenerated on every restart (`agent_spec.ex:390-393`) — not durable. `team_name`/`name` (straight from `TEAM.json`, re-read every boot) are the durable pair. `Sidecar.Tools.Beads.resolve_actor/1` is the one shared implementation every mutating tool calls, rather than four private copies of the same four lines:


### `Planck.Web.Live.SidecarWidget` — generic LiveComponent (new, `planck_cli`)

This is the one place that decides the opaque term is HTML — that assumption belongs here, not upstream in `planck_agent`/`planck_headless`.

**Three real bugs found during Phase 3 implementation, not just style fixes — the original sketch (kept below for history) doesn't work as written:**

1. **`Phoenix.LiveComponent` has no `handle_info/2`.** Confirmed by the compiler, not a style opinion: a component has no process of its own, so a message a component's `Phoenix.PubSub.subscribe/2` call causes to be delivered arrives at the *parent* LiveView's `handle_info/2` — never at anything defined on the component module. The parent must route it in with `send_update/3`. The component's own reaction has to be a second `update/2` clause, not `handle_info/2`.
2. **`Phoenix.PubSub.subscribe/2` is not idempotent — confirmed empirically**, not assumed: subscribing the same pid N times to the same topic delivers N copies of every broadcast. Since `update/2` reruns on every parent re-render (not just first mount), the sketch below would leak duplicate subscriptions — and would also needlessly repeat the RPC pull on every unrelated parent render, contradicting the "pull once, then push" design.
3. **`Phoenix.LiveComponent` also has no termination callback.** Checked directly (`Phoenix.LiveComponent.behaviour_info(:callbacks)` lists only `update_many/1, update/2, mount/1, render/1, handle_event/3, handle_async/3`), while chasing "how does the component unsubscribe when the modal closes." It can't — there's no hook. Combined with bug 1, this means the component must never subscribe at all: subscribe/unsubscribe moves entirely to the *owning LiveView*, tied to its own explicit open/close event handlers (a LiveView has a real process and real lifecycle control), not to the component's mount/unmount. This also resolves open question 1 below ("Widget lifecycle / cleanup") for the generic case, not just beads.

Corrected — `SidecarWidget` itself now only pulls and receives pushes, no PubSub of its own:

```elixir
defmodule Planck.Web.Live.SidecarWidget do
  use Planck.Web, :live_component

  # The parent re-passes widget_id on every one of its own re-renders, not
  # just first mount, so this guards against re-issuing the RPC pull (and
  # clobbering html pushed since via send_update) on every unrelated parent
  # render.
  def update(%{widget_id: id}, %{assigns: %{widget_id: id}} = socket) do
    {:ok, socket}
  end

  def update(%{widget_id: id}, socket) when is_binary(id) do
    socket =
      case Planck.Headless.Widgets.render(id, socket.assigns.myself) do
        {:ok, html} -> assign(socket, html: html, error: nil)
        {:error, reason} -> assign(socket, html: nil, error: reason)
      end

    {:ok, assign(socket, :widget_id, id)}
  end

  # Forwarded by the owning LiveView's own handle_info/2 via
  # send_update(SidecarWidget, id: "sidecar-widget-modal", html: new_html) —
  # see bugs 1 and 3 above. This LiveView is Phase 6/7's job, not this phase's.
  def update(%{html: html}, socket), do: {:ok, assign(socket, html: html, error: nil)}

  def update(_assigns, socket), do: {:ok, socket}

  def handle_event("widget_action", params, socket) do
    case Planck.Headless.Widgets.dispatch_action(socket.assigns.widget_id, params["action"], params["args"]) do
      :ok -> LiveToast.send_toast(socket, :info, "#{params["action"]} succeeded")
      {:error, reason} -> LiveToast.send_toast(socket, :error, "#{params["action"]} failed: #{inspect(reason)}")
    end

    {:noreply, socket}
  end

  def render(%{error: :sidecar_not_connected} = assigns) do
    ~H"""
    <div id={"widget-#{@widget_id}"} class="text-muted-foreground text-xs">
      Sidecar not connected — this widget will reload once it reconnects.
    </div>
    """
  end

  def render(assigns) do
    ~H"""
    <div id={"widget-#{@widget_id}"}><%= Phoenix.HTML.raw(@html) %></div>
    """
  end
end
```

`Phoenix.HTML.raw/1`, not bare `raw/1` — confirmed this codebase never imports `Phoenix.HTML` into `live_component`/`live_view` (only into the `html` macro), so every existing call site uses the qualified name (`chat_component.ex`'s `render_markdown/1`, for one). Bare `raw/1` doesn't compile here.

### One modal, not a registry — where subscribe/unsubscribe actually lives

`planck_cli` has no compile-time knowledge of widget ids (sidecars, including future custom ones, define their own), so rather than a dynamic component registry keyed by widget id, the WebUI hosts a single, fixed-id `SidecarWidget` instance — mirroring `Planck.Web.Live.SetupModal`'s existing pattern — re-targeted at whichever `widget_id` is currently open. Implemented in `SessionLive`:

```elixir
# open_widget arrives via send(self(), {:open_widget, ...}) from
# Planck.Web.Live.ChatComponent, not a direct phx-click on SessionLive
# itself — the button lives inside that nested component, which needs to
# resolve widget_id from its own `entries` assign before forwarding.
def handle_info({:open_widget, %{widget_id: widget_id}}, socket) do
  # Opening a second widget without closing the first would otherwise leave
  # the old topic subscribed forever (only close_widget unsubscribes) —
  # treat opening a different widget as an implicit switch.
  if id = socket.assigns.open_widget_id do
    Phoenix.PubSub.unsubscribe(Planck.Agent.PubSub, "sidecar:widget:#{id}")
  end

  Phoenix.PubSub.subscribe(Planck.Agent.PubSub, "sidecar:widget:#{widget_id}")
  {:noreply, assign(socket, :open_widget_id, widget_id)}
end

# No phx-target on the close button (it lives in SidecarWidget's own chrome,
# mounted at the SessionLive template level) — bubbles directly here, same
# as every other modal's close button in this codebase.
def handle_event("close_widget", _params, socket) do
  if id = socket.assigns.open_widget_id do
    Phoenix.PubSub.unsubscribe(Planck.Agent.PubSub, "sidecar:widget:#{id}")
  end

  {:noreply, assign(socket, :open_widget_id, nil)}
end

def handle_info({:widget_rendered, widget_id, html}, socket) do
  if socket.assigns.open_widget_id == widget_id do
    send_update(Planck.Web.Live.SidecarWidget, id: "sidecar-widget-modal", html: html)
  end

  {:noreply, socket}
end
```

The broadcast payload names the widget (`{:widget_rendered, id, html}`, not just `{:widget_rendered, html}`) — routing correctness depends on that, not on the component id, since the component id is always `"sidecar-widget-modal"` regardless of which widget is currently shown.

### Container type — modal only, for now

`Planck.Agent.Widget` supports declaring `:drawer`/`:fullscreen` via `container/0` (see the design decisions above), but as of this version `SidecarWidget` doesn't branch on it at all — it unconditionally renders modal chrome (backdrop, box, close button, Escape-to-close), mirroring `ModelSelectorModal`'s structure directly. This is a deliberate simplification, not an oversight: `:modal` is the only container kind that's ever actually requested today, so `SessionLive` doesn't fetch `Planck.Headless.Widgets.container/1` before opening one. When a second container kind is actually built, that's the point where `SessionLive`'s `open_widget` handler needs to fetch the container type and choose between differently-chromed components — not before.

The `LiveToast.send_toast/3` call above is still Phase 14 work — the actual Phase 3 implementation deliberately omits it (dispatches the action and returns `{:noreply, socket}` with a comment noting the deferral), since `live_toast` isn't a dependency yet. This sketch shows the eventual end state, not what phase 3 alone produces.

Previously, a bare `{:ok, html} = Planck.Headless.Widgets.render(...)` match here would raise a `MatchError` and crash the LiveView if the sidecar was down — `Planck.Headless.Widgets.render/2` already correctly returns `{:error, :sidecar_not_connected}` (mirroring `Secrets`'s dispatch), the consumer just never branched on it. Fixed above; no change needed to the RPC layer itself.

**Done.** Not installed into the main `planck` image at all — beads runs as two new services in `planck_docker/compose.yml`, matching the existing `typesense`/`searxng`/`tika`/`vault` convention (one process, one purpose, per service; Docker's own container lifecycle handles supervision, no new Elixir-side process-management code needed).

**`planck_docker/beads/Dockerfile` + entrypoint (done).** Installs the `bd` binary from beads' own GitHub releases (not the Homebrew formula — this runs on Linux inside the container), for whichever of `linux_amd64`/`linux_arm64` matches Docker's `TARGETARCH` build arg, with its sha256 checksum (from the release's own `checksums.txt`) verified before extracting, not just downloaded and trusted. The entrypoint has to check for an existing `.beads/config.yaml` before calling `bd init` at all — confirmed empirically that `bd init --server` is **not** idempotent on its own (a second call against an already-initialized workspace exits 1 with `"This workspace is already initialized"`):

```sh
#!/bin/sh
set -e
mkdir -p /data/.beads
export BEADS_DIR=/data/.beads
if [ ! -f "$BEADS_DIR/config.yaml" ]; then
  bd init --server --server-host dolt --server-port 3306 --quiet --skip-agents
fi
echo "$BEADS_TOKEN" > /run/beads-token
exec bd serve --addr 0.0.0.0:8377 --allow-non-loopback --allowed-host beads --auth-token-file /run/beads-token
```

**Auth — the other real blocker this design missed at first.** `bd serve --help`, read carefully rather than skimmed: *"The DNS-rebinding check answers only to loopback spellings and the bind address, so a client dialing a service name gets 400 on every request; enumerate the names it dials with `--allowed-host`"* — exactly what `Sidecar.Beads` does, dialing `http://beads:8377`. And separately, *"`--allow-non-loopback` REQUIRES a token file"* — traffic arriving over the Docker bridge network from the `planck` container isn't loopback traffic from `bd serve`'s point of view, even though it's internal to the stack. Without `--allow-non-loopback --allowed-host beads --auth-token-file`, every single call from the sidecar would 400. `BEADS_TOKEN` is one shared secret (generated once, same pattern as `TYPESENSE_API_KEY` — no bootstrap round-trip needed, unlike `AGENT_VAULT_TOKEN`'s setup-container dance), passed to both services; `Sidecar.Config.beads_token/0` and the `Authorization: Bearer <token>` header itself are added when `Sidecar.Beads`'s HTTP client is actually built (Phase 12) — the config key alone landed in this phase (Phase 11).

**Install scripts — done.** `docs/install_docker.sh`, `docs/install_docker.ps1`, and `dev_docker.sh` all got the same directory-creation and `BEADS_TOKEN` random-value generation `typesense-data`/`TYPESENSE_API_KEY` already had, added right alongside the existing entries in each script's directory list and `.env`-writing section.

**Consequence worth noting:** since beads' actual data now lives in the `dolt`/`beads` services' own volumes, not the workspace bind-mount, there's no `.beads/` directory inside `/workspace` at all — the Typesense-exclusion fix from earlier in this design pass (adding `.beads` to `Sidecar.Watcher`'s `@excluded_dirs`) is now unnecessary. Nothing to exclude.

## 2. `{:custom, :ui}` Messages

### Problem

A tool's result is plain text sent straight to the LLM (`Planck.Agent.MessageBuilder.build_tool_result/1` requires `{:ok, string} | {:error, term}`). There's currently no way for a tool to also attach a UI affordance — e.g. "open the widget you just updated" — without either polluting the model's context with UI-only data, or hand-rolling per-tool special cases in the LLM-facing serializer.

### Design decision

Reuse the existing `{:custom, atom()}` message-role convention, already documented in `Planck.Agent.Message` (`planck_agent/lib/planck/agent/message.ex:6-7`) and already used for `{:custom, :summary}` (checkpoints) and `{:custom, :agent_response}` (inter-agent replies). `Message.to_ai_messages/1` already has a catch-all that drops any unrecognized custom role before the context reaches the LLM:

```elixir
%__MODULE__{role: {:custom, _}} -> []
```

So `{:custom, :ui}` gets "invisible to the model" for free. **No changes to `planck_ai`'s adapter are needed.**

### Tool result contract

A tool's `execute_fn` may return a 3-element form instead of the normal 2-element one. The third element is a **map**, not a keyword list — `%{ui: ui_content()}`, not `ui: ui_content()`:

```elixir
{:ok, text}                                                                # unchanged — existing tools keep working as-is
{:ok, text, %{ui: %{kind: :text, text: note}}}                             # new — a UI-only note, no widget at all
{:ok, text, %{ui: %{kind: :widget, label: label, widget: widget_id, data: initial_snapshot}}}  # new — a widget-opening button
{:error, reason}                                                           # unchanged
```

**`ui_content` is deliberately not just `%{widget: id, data: term()}`.** That shape conflated two different things: what the widget itself contains (already solved — `Planck.Agent.Widget.render/1`) and what shows up *in the chat transcript* to represent the tool's UI side effect. A `kind`-tagged map keeps those separate and covers a case the single-shape version couldn't: a UI-only note with no widget involved at all (e.g. "Marked 3 beads as done.") — not everything a tool wants to show the human is "open a widget."

- `%{kind: :text, text: "..."}` — rendered as plain UI-only text in the chat, invisible to the LLM. No widget.
- `%{kind: :widget, label: "...", widget: widget_id, data: initial_snapshot}` — rendered as a button labeled `label`. `label` is sidecar-authored and human-readable (e.g. `"View kanban board"`, not a generic "Open widget") — the tool decides what invites the click, the widget (via its own `render/1`) decides what's inside once opened. `data` is optional/opaque, same rationale as before: avoids a round-trip through `render/1` for the very first paint, nothing more.

### Implementation

`finish_tool_execution/2` (`planck_agent/lib/planck/agent.ex:681`) strips the `ui:` element before building the plain tool-result message, then persists a sibling `{:custom, :ui}` message for any result that carried one. The `ui_content` map goes into the new message's **metadata**, not its `content` — matching the existing `{:custom, :summary}`/`{:custom, :agent_response}` convention of keeping `content` within `Planck.AI.Message.content_part()`'s closed type and putting custom structured extras in `metadata` instead (a bare `{:ui, id, payload}` tuple in `content`, as an earlier draft of this sketch had it, isn't a valid `content_part()` and would be a real Dialyzer-visible type mismatch):

```elixir
defp finish_tool_execution(results, state) do
  results = Enum.reverse(results)

  tool_result_msg =
    results
    |> Enum.map(fn {id, result} -> {id, strip_ui(result)} end)
    |> MessageBuilder.build_tool_result()
    |> then(&persist_message(state, &1))

  ui_msgs =
    for {id, {:ok, _text, %{ui: content}}} <- results do
      Message.new({:custom, :ui}, [], %{tool_call_id: id, ui: content})
      |> then(&persist_message(state, &1))
    end

  %{state | messages: state.messages ++ [tool_result_msg | ui_msgs], status: :streaming}
end

defp strip_ui({:ok, text, %{ui: _}}), do: {:ok, text}
defp strip_ui(result), do: result
```

`MessageBuilder.build_tool_result/1` is **unchanged** — it never sees the `ui:` element, so its truncation and `is_binary`/`inspect` handling stays exactly as it is today.

### Display

**Done.** `Planck.Web.Live.ChatEntries.classify_row/4` gains a clause parallel to the existing `{:custom, :summary}` / `{:custom, :agent_response}` handling, reading `metadata` (not `content`) and dispatching to a `ui_entry/4` helper that branches on `kind` — `%{kind: :text, ...}` builds a `:ui_text` entry, `%{kind: :widget, ...}` builds a `:ui_widget` entry (`:label`, `:widget`, `:widget_data`).

**A real ordering problem surfaced and got fixed here, not deferred:** `finish_tool_execution/2` always persists the batch's combined `:tool_result` message *before* any sibling `{:custom, :ui}` messages (Section 2's Implementation), so relying on raw row order would put every UI trigger after every tool result in the same batch — `Tool A, Tool B, UI A, UI B` instead of the `Tool A, UI A, Tool B, UI B` a human reading the transcript expects. Fixed with `insert_ui_entries/1`: `{:custom, :ui}` rows classify into an internal `%{__ui__: true, tool_id:, entry:}` marker (mirroring the existing `tool_result_marker` pattern from `pair_tool_results/1`), which then gets spliced in right after the `:tool` entry sharing its `tool_id` — matching by id, not by position. Runs *before* `pair_tool_results/1` in `build/3`'s pipeline (needs the `:tool` entries still present to splice after; `pair_tool_results/1` only enriches them in place, doesn't move them, so order between the two steps doesn't matter for correctness, but `insert_ui_entries/1` first was simpler to reason about). A marker whose tool call is missing (shouldn't normally happen) is appended at the end rather than silently dropped.

The chat template renders plain text for `:ui_text` entries, and a button (using `label`) for `:ui_widget` entries. Clicking the button doesn't mount `SidecarWidget` directly from `ChatComponent`'s own template — the button fires a local `"open_widget"` event (`phx-target={@myself}`), which `ChatComponent.handle_event/3` resolves against its own `entries` assign (to get `widget_id`) and forwards via `send(self(), {:open_widget, %{widget_id: ...}})`, matching the same forward-to-parent pattern this codebase already uses for `"open_edit"` → `{:open_edit_message, ...}`. `widget_data` from the tool call is *not* threaded through to `SidecarWidget` — it always does its own RPC pull on open regardless (Phase 3's design), so the seeded-snapshot optimization described in Section 1's tool-result contract isn't actually consumed by anything yet.

**`Planck.Web.Live.SessionLive` implements the subscribe/forward contract `SidecarWidget`'s moduledoc documents but doesn't implement itself** — see Section 1's "One modal, not a registry" subsection for the actual `handle_info`/`handle_event` code. Without the forwarding half, mounting the widget from chat would show its first paint correctly and then never update again — silently, no error, exactly the kind of gap Phase 15's "confirm each live-updates via PubSub" verification step is meant to catch. Without the unsubscribe-on-switch half, opening a second widget without closing the first would leak the old topic's subscription. Both landed in this same phase as the mount itself, not later.

**Still true after this phase, unchanged:** nothing yet broadcasts `{:widget_rendered, ...}` — that's the sidecar-side widget owner's job (`Sidecar.Beads.broadcast_refresh/0`, Phase 12/13), so a widget's first paint works end to end but live updates don't until those phases land.

### New `entry_type`

**Done.** `:ui_text` and `:ui_widget` are added to `Planck.Web.Live.ChatEntries.entry_type/0` — `:ui_text` with a `:text` key, `:ui_widget` with `:label`, `:widget`, and `:widget_data`.

### Proof of concept: beads

The deliverable for this version. `bd_ready` (Section 1) is the trigger: its `execute_fn` returns the 3-element form, naming the widget without duplicating its data:

```elixir
{:ok, format_ready_beads(),
 %{ui: %{kind: :widget, label: "View kanban board", widget: "beads-board", data: nil}}}
```

`finish_tool_execution/2` strips the `ui:` element for the LLM-facing tool result exactly as described above, and persists a sibling `{:custom, :ui}` message with `metadata: %{tool_call_id: id, ui: %{kind: :widget, label: "View kanban board", widget: "beads-board", data: nil}}`. `ChatEntries` renders a button labeled "View kanban board"; clicking it opens `Planck.Web.Live.SidecarWidget` (Section 1) with `widget_id: "beads-board"`, which does its own RPC pull (`Planck.Headless.Widgets.render/2`) for the first paint and then lives off the `"sidecar:widget:beads-board"` PubSub topic — no data needed to have arrived with the tool result.

**Not in this version:** `write_skill` adopting the `ui:` contract. An earlier draft of this spec had it as the proof of concept, including a required fix to `Sidecar.SkillReflector.Runner`'s `:tool_end` pattern match (`planck_docker/sidecar/lib/sidecar/skill_reflector/runner.ex:87`, which matches the raw 2-tuple result and would silently stop firing against the new 3-tuple form). That fix is still correct whenever `write_skill` does adopt this contract — just not now.

```elixir
def render_markdown(text) when is_binary(text) do
  case MDEx.to_html(text, extension: [table: true, autolink: true], render: [hardbreaks: true]) do
    {:ok, html} -> Phoenix.HTML.raw(html)
```

## 4. Sidecar Widget Localization

### Problem

Everything `planck_cli` renders is already localized via `Planck.Web.Gettext` — except the HTML a sidecar-rendered widget (Section 1's beads board) produces, which was hardcoded English with no translation path at all. Not a beads-specific gap: any future widget kind would hit the same wall.

### Why this isn't "just add Gettext to the sidecar"

The sidecar runs as a genuinely separate distributed Erlang node from `planck_headless`/`planck_cli` (`Planck.Headless.SidecarManager` talks to it via `:rpc.call`, confirmed by reading its source, not assumed) — it is not the same VM. Two consequences neither fully addressed nor fully caught until this pass:

1. `Gettext.put_locale/2`'s locale is process-local. It never crosses an RPC boundary implicitly, so the sidecar can't just "know" what locale the connected browser session is using.
2. The obvious fix — thread a `locale` argument through the widget RPC dispatch chain into `c:Planck.Agent.Widget.render/1` — touches that behaviour's callback signature, which every widget kind implements, not just beads. Rejected for the same reason Section 1 didn't thread a `:client` opt through it either: a test-only or plumbing-only concern doesn't get to grow a shared, real dispatch contract.

### Design: a plain cached fact, pushed on every request, decoupled from any i18n library

`Planck.Agent.Sidecar` (in `planck_agent`, loaded on both nodes, already holding one `:persistent_term`-cached fact via `discover/0`) gained two more module-level functions, callable via the same `:rpc.call` surface `list_widgets/0`/`widget_render/2`/etc. already use:

```elixir
# planck_agent/lib/planck/agent/sidecar.ex
@locale_key {__MODULE__, :locale}

@spec set_locale(String.t()) :: :ok
def set_locale(locale) do
  case :persistent_term.get(@locale_key, nil) do
    ^locale -> :ok
    _ -> :persistent_term.put(@locale_key, locale)
  end
end

@spec get_locale() :: String.t()
def get_locale, do: :persistent_term.get(@locale_key, "en")
```

Not tied to Gettext or any other i18n library at all — this is just "the current locale," a plain string. `set_locale/1` is written to be idempotent (absent → set; present and equal → no-op; present and different → update) because the caller, `Planck.Web.Locale.Plug`, has no cheap way to know in advance whether the locale it just resolved is actually different from last time, and calls it on **every request**, not just on change:

```elixir
# planck_headless/lib/planck/headless/locale.ex — mirrors Widgets' dispatch shape
defmodule Planck.Headless.Locale do
  def set(locale) do
    case Planck.Headless.SidecarManager.node() do
      nil -> :ok
      node -> case :rpc.call(node, Planck.Agent.Sidecar, :set_locale, [locale], 5_000) do
        {:badrpc, _reason} -> :ok
        :ok -> :ok
      end
    end
  end
end
```

```elixir
# planck_cli/lib/planck/web/locale/plug.ex — the one new call site
def call(%Plug.Conn{} = conn, %Config{} = config) do
  config = Config.select_locale(conn, config)
  Gettext.put_locale(config.gettext, config.selected)
  Planck.Headless.Locale.set(config.selected)   # new
  conn |> assign(:locale, config.selected) |> put_session(:locale, config.selected)
end
```

Always returns `:ok` and never blocks the request meaningfully longer than a 5s worst case — a disconnected or slow sidecar must not fail the page load this runs inside of. This is the same synchronous-RPC-from-the-request-path tradeoff `Planck.Headless.Widgets.render/2`/`dispatch_action/3` already accept (a 30s timeout there), not a new pattern.

**A nice property of "push every request, idempotent remote side" that a simpler "push once at boot" design wouldn't have had:** since `config.selected` is already the *fully resolved* locale regardless of which of the plug's four priority tiers produced it, the sidecar ends up correctly tracking session-level and `Accept-Language`-level locale changes too, not just the top-priority `config.json` value — with no extra propagation logic, because every request re-pushes whatever was actually resolved.

### `Sidecar.Gettext` — a separate catalog, by necessity not preference

```elixir
# planck_docker/sidecar/lib/sidecar/gettext.ex
defmodule Sidecar.Gettext do
  use Gettext.Backend, otp_app: :sidecar
end
```

Cannot be the same catalog as `Planck.Web.Gettext` even in principle — they're compiled into and read by two different OTP releases running on two different nodes. `{:gettext, "~> 1.0"}` added to `planck_docker/sidecar/mix.exs`; translation files live at `priv/gettext/<locale>/LC_MESSAGES/default.po`, `en`/`es` seeded (matching `planck_cli`'s own supported locales), generated via the standard `mix gettext.extract` + `mix gettext.merge priv/gettext --locale <locale>` workflow, not hand-written.

A widget module uses `use Gettext, backend: Sidecar.Gettext` (Gettext 1.0's macro-based API — not the older `import`-based one, which doesn't expose `pgettext/2`) to get `gettext/1`/`pgettext/2` bound to it:

```elixir
# planck_docker/sidecar/lib/sidecar/widgets/beads.ex
use Gettext, backend: Sidecar.Gettext

def render(myself, opts) do
  Gettext.put_locale(Sidecar.Gettext, Planck.Agent.Sidecar.get_locale())
  # ...pgettext("button label", "Claim"), pgettext("bead widget", "New task"), etc.
end
```

Set on every call, not once — a widget render is stateless from one call to the next and has no other way to know which locale to use. Every literal label in the beads board (button text, placeholders, "none", "priority", and the two fixed status column headers "open"/"in progress") is wrapped; bead **data** itself (titles, ids, assignee names) is never translated, obviously — that's user content, not UI copy.

## Open design questions for review

1. ~~Widget lifecycle / cleanup~~ **Resolved, generically, not just for beads.** `Phoenix.LiveComponent` has no termination callback at all (checked directly — `terminate/2` isn't in `behaviour_info(:callbacks)`), so there's no hook to unsubscribe from on unmount regardless of what a given widget does in the background. Fix: `SidecarWidget` never subscribes to PubSub itself; the owning LiveView's own explicit `open_widget`/`close_widget` event handlers own the subscribe/unsubscribe lifecycle (see Section 1, "One modal, not a registry").
2. ~~Multiple simultaneous widget instances~~ **Resolved** — one beads DB per Planck installation means every open widget is necessarily showing the same data, so sharing one subscription per `id` isn't a design choice, it's the only correct behavior. Confirmed, not just assumed.
3. ~~Error handling~~ **Resolved** — `SidecarWidget.update/2` previously did a bare `{:ok, html} = ...` match that would crash on `{:error, :sidecar_not_connected}`; fixed to branch on both and render a "sidecar not connected" state (see Section 1).
4. ~~External mutation staleness~~ **Mostly resolved, and the remaining gap shrank further.** The actual risk wasn't external `bd` CLI usage, it was the four mutating *tools* (`bd_claim`/`bd_create`/`bd_delete`/`bd_done`) running through `execute_tool/4`, a separate path from the widget's own `handle_action/2`, and not broadcasting a refresh. Fixed: `Sidecar.Beads.broadcast_refresh/0` is shared and called by both. Now that beads lives in its own `dolt`/`beads` services rather than the workspace filesystem, "someone shelling into the container and running `bd` directly" isn't really possible anymore — there's no `.beads/` to reach from inside the `planck` container at all, only the HTTP API. The `file_system`-watcher idea is accordingly dropped; if true push-based external-mutation detection is ever wanted, `bd serve`'s own `events.watch`/`events.list` capability (discovered but not explored — see Section 1) is the path, not a filesystem watcher.
5. ~~Flash/toast support~~ **Resolved** — adopting `live_toast` (`planck_cli`-only dependency; the sidecar never touches a `Socket`/`Conn` so it needs none) instead of vanilla flash, specifically because `send_toast/3` works from a `LiveComponent`'s `handle_event/3` without the parent-propagation workaround the spike would have otherwise required.
