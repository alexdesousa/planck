# Planck v0.1.14 — Spec

## Overview

Two related capabilities that let a sidecar put real UI in front of the user, instead of being limited to plain-text tool results:

1. **Sidecar widgets** — a sidecar can render its own markup (real Phoenix Components/HEEx) and stream it into the main WebUI, with live updates pushed back over PubSub and user actions dispatched back to the sidecar over RPC.
2. **`{:custom, :ui}` messages** — a tool call can attach a UI-only side effect (e.g. "here's a button that opens a widget") to the chat transcript without that side effect ever reaching the LLM's context.

Both were designed against a concrete motivating case — integrating [beads](https://github.com/gastownhall/beads), a task/issue tracker for coding agents, as a sidecar tool with a visual kanban board — and **that integration is this version's deliverable**, not deferred follow-up work. Earlier drafts of this spec planned `write_skill` as the proof of concept instead, since it needed only Section 2; that was dropped because `write_skill` only fires when an LLM decides to call it (or via the `SkillReflector`'s async mini-agent loop), which makes it awkward to trigger deterministically in a test. `bd` is a plain CLI — a `bd_ready`-style tool can be exercised directly, end to end, without depending on model behavior at all. It's more work (it needs both sections, not just Section 2), but it's the better validation target.

### Explicitly not touched

- **Credentials / `SetupModal`** — during design it was tempting to move the agent-vault credential UI onto this same widget mechanism. Rejected: `Planck.Headless.Secrets` already dispatches transparently between `EnvFile` (standalone) and `Sidecar.Secrets.AgentVault` (Docker) via `:rpc.call/5`, so `SetupModal.KeysStep` is already one code path for both backends. Introducing widget-streaming there would split one maintained implementation into two. Leave as-is.
- **Third-party/MCP-registered widgets** — this spec assumes the sidecar shipping markup is first-party and bundled by Planck (same trust level as `planck_agent` itself). If a future `connect_mcp(url)` mechanism lets an arbitrary external MCP server register a widget, shipping raw HTML from it becomes an XSS vector, and that path needs a data-only/fixed-catalog renderer instead of what's described here.

---

## 1. Sidecar Widgets

### Problem

A sidecar tool's only current output is plain text in a tool-result bubble (`Planck.Agent.Sidecar.execute_tool/4` → a string). For sidecar-owned state that's inherently visual or long-lived (a task board, a dependency graph, a live log), there's no way to show anything beyond that text, and no existing abstraction to build on the way `Planck.Agent.Secrets` already covers credentials.

### Design decisions

- **The sidecar ships markup, not just data.** A widget module is allowed to use `Phoenix.Component`/HEEx to build its own UI. This is the point of the feature — new widget *kinds* don't require a `planck_cli` release.
- **Never send `%Phoenix.LiveView.Rendered{}` (or any closures) across the RPC boundary.** It embeds anonymous functions for diff-tracking; funs sent between distributed Erlang nodes only execute correctly if the receiving node has byte-identical compiled code for that module, which defeats independent sidecar versioning. Instead, the sidecar flattens its own render to a plain HTML string (`Phoenix.HTML.Safe.to_iodata/1` → `IO.iodata_to_binary/1`) before the RPC call returns. Only ever a `binary()` crosses the wire.
- **Pull for the initial paint, push for updates.** Opening a widget does one RPC call for a first snapshot; after that, the sidecar broadcasts fresh HTML over `Phoenix.PubSub` whenever its underlying state changes. This mirrors the already-proven pattern in `sidecar/lib/sidecar/session_indexer.ex`, which already subscribes to a topic on `Planck.Agent.PubSub` from the sidecar node — cross-node PubSub on a shared topic name is existing, working infrastructure, not new.
- **Actions round-trip through the same broadcast, not a synchronous reply.** Clicking a button in a widget dispatches an RPC call to the sidecar; the sidecar mutates its own state and then broadcasts the refreshed HTML on the widget's topic. Every open viewer (including the one that clicked) updates from that broadcast. No special-casing "my own click."
- **`phx-target` needs the LiveComponent's CID baked in.** The sidecar's render call has no socket/component context, so `JS.push(..., target: @myself)` can't resolve `@myself` on the sidecar side. The CID is passed in as a plain argument and rendered into the HTML as a literal `phx-target` attribute value.
- **`Tool` and `Widget` stay separate behaviours — but widget discovery is derived from `tools/0`, not a second declared list.** `Planck.Agent.Widget` keeps its own identity (a widget is not a tool: different return shape and different dispatch path, see below). What's removed is the *second, independent* `widgets/0` callback: `Planck.Agent.Tool.t()` gains an optional `:widget` field holding the *module* that implements `Planck.Agent.Widget`, and `list_widgets/0` filters `tools/0` for tools that have one. One thing to declare per pairing, not two.
- **Declaration is derived; dispatch still isn't shared with `execute_tool/4`.** A widget's render/action calls do not reuse the LLM tool-execution path, for two concrete reasons: (1) `execute_tool/4` results flow into `finish_tool_execution/2`, which appends to the agent's actual message history sent back to the LLM — a human clicking a widget button has no corresponding assistant-issued `tool_call`, and faking one to satisfy that invariant is worse than just having separate RPC entry points; (2) `execute_fn`'s contract (`{:ok, string} | {:error, string}`) is meant for the model's context, while a widget's output is meant for a UI surface to render — a different kind of value entirely.
- **A widget declares its own container type — optionally, via `use`.** `Planck.Agent.Widget` gains an *optional* `container/0` callback (`@optional_callbacks container: 0`) returning `:modal | :drawer | :fullscreen`. `use Planck.Agent.Widget` (instead of a bare `@behaviour Planck.Agent.Widget`) injects `@behaviour` plus a default `container/0` returning `:modal`, `defoverridable` for widgets that want something else once a second container kind exists. This is a real injected function, not a caller-side default: an earlier version of this design had `Planck.Agent.Sidecar.widget_container/1` fall back to `:modal` via `function_exported?/3` when the widget didn't implement `container/0`, so a direct call to a bare-behaviour widget's `container/0` would raise while the RPC path silently returned `:modal` — two different answers depending on how you asked. Rejected in favor of the macro precisely so both paths agree: calling `container/0` directly behaves identically to calling it through `widget_container/1`. The cost: a widget written with a bare `@behaviour` (no `use`) gets no default at all — that's an accepted, deliberate tradeoff, not an oversight.
- **`planck_agent` does not know its widgets produce HTML.** `Planck.Agent.Widget` and `Planck.Agent.Sidecar` live in `planck_agent`, which is UI-agnostic today (its only Phoenix-adjacent dependency is `phoenix_pubsub`; no `phoenix_live_view`/`Phoenix.Component`). The behaviour's render callback returns an **opaque `term()`** — `planck_agent` never inspects or interprets it, only RPCs it through. `planck_cli` is the one place that assumes the term is an HTML string and does `raw/1` on it; the sidecar module is the one place that chooses to `use Phoenix.Component` to build one. This was weighed against making the contract carry structured *data* instead of markup (fully renderer-portable, but reintroduces "new widget kind needs a `planck_cli` release" — the exact cost the "sidecar ships its own markup" decision above was meant to avoid) and rejected for now: `planck_tui` doesn't exist yet, so there's no second UI surface to design portability against. If one shows up, a widget module written for `planck_cli` won't automatically work there — a `planck_tui`-targeting widget would need its own separate module producing whatever `planck_tui` expects, reusing the same `Planck.Agent.Widget` behaviour and the same `:widget` field on `Tool`, just with a different implementation. Revisit if and when that becomes real instead of hypothetical.

### `Planck.Agent.Sidecar` — `list_widgets/0` derived from `tools/0`, no separate callback

```elixir
# planck_agent/lib/planck/agent/sidecar.ex — no new @callback
def list_widgets, do: discover() |> apply(:tools, []) |> Enum.filter(& &1.widget) |> Enum.map(& &1.widget)
def widget_render(widget_id, myself), do: fetch_widget!(widget_id).render(myself)
def widget_action(widget_id, action, args), do: fetch_widget!(widget_id).handle_action(action, args)
def widget_container(widget_id), do: fetch_widget!(widget_id).container()
```

`Planck.Agent.Widget` behaviour — `render/1`'s return value is opaque to `planck_agent`, `container/0` is optional and macro-provided:

```elixir
@callback id() :: String.t()
@callback render(myself :: term()) :: term()   # opaque — planck_agent never inspects this
@callback handle_action(action :: String.t(), args :: map()) :: :ok | {:error, term()}
@callback container() :: :modal | :drawer | :fullscreen   # optional
@optional_callbacks container: 0

defmacro __using__(_options) do
  quote do
    @behaviour Planck.Agent.Widget
    @impl Planck.Agent.Widget
    def container, do: :modal
    defoverridable container: 0
  end
end
```

Widgets use `use Planck.Agent.Widget`, not a bare `@behaviour Planck.Agent.Widget`, to get the default — `widget_container/1` above calls `.container()` directly with no `function_exported?/3` fallback, so a bare-`@behaviour` widget that skips implementing `container/0` raises there too, consistently with a direct call.

### Beads tool + widget (the deliverable)

```elixir
# planck_docker/sidecar/lib/sidecar/tools/beads_ready.ex — the tool
defmodule Sidecar.Tools.BeadsReady do
  def tool do
    Planck.Agent.Tool.new(
      name: "bd_ready",
      description: "List beads with no open blockers.",
      parameters: %{"type" => "object", "properties" => %{}},
      execute_fn: fn _agent_id, _id, _args ->
        # format_ready_beads/0 wraps Sidecar.Beads.ready/1 (GET /v0/beads/ready)
        # and formats the {:ok, %{"items" => [...]}} result as text for the model.
        {:ok, format_ready_beads(), ui: %{widget: "beads-board", data: nil}}
      end,
      widget: Sidecar.Widgets.Beads
    )
  end
end
```

`ui.data` is `nil` here rather than a real snapshot — the widget pulls its own first paint via `Planck.Agent.Widget.render/1` when opened (Section 1's pull-then-push model), so there's no need to duplicate the same data into the tool result too. Contrast with the earlier `write_skill` sketch, where `ui.data` carried the *entire* payload because there was no RPC pull step at all.

```elixir
# planck_docker/sidecar/lib/sidecar/widgets/beads.ex — the widget
defmodule Sidecar.Widgets.Beads do
  use Phoenix.Component   # this module's choice — planck_agent doesn't require or know about it
  @behaviour Planck.Agent.Widget

  def id, do: "beads-board"

  # fetch_beads/0 wraps Sidecar.Beads.list(status: ["open", "in_progress"])
  # — the generic list/1 endpoint, not ready/1. The board shows in_progress
  # work (and who's assigned) too, which ready/1 deliberately excludes.
  def render(myself) do
    assigns = %{beads: fetch_beads(), myself: myself}

    ~H"""
    <div class="grid grid-cols-3 gap-2">
      <%= for {status, beads} <- @beads do %>
        <div class="border-2 border-border p-2">
          <p class="font-bold text-xs"><%= status %></p>
          <%= for bead <- beads do %>
            <div class="text-xs"
              phx-click={JS.push("widget_action", value: %{action: "claim", args: %{id: bead["id"]}}, target: @myself)}>
              <%= bead["title"] %>
            </div>
          <% end %>
        </div>
      <% end %>
    </div>
    """
    |> Phoenix.HTML.Safe.to_iodata()
    |> IO.iodata_to_binary()
  end

  def handle_action("claim", %{"id" => id, "assignee" => assignee}) do
    # An explicit "actor"/assignee field, not bd's own ambient identity —
    # meaningless here since every call would otherwise share one identity.
    # The HTTP API's own concurrency control (arbitrated server-side, not a
    # client-side optimistic guard) protects against two callers claiming
    # the same ready bead at once.
    Sidecar.Beads.claim(id, assignee)
    Sidecar.Beads.broadcast_refresh()
  end

  def handle_action("create", %{"title" => title, "actor" => actor}) do
    Sidecar.Beads.create(title, actor)
    Sidecar.Beads.broadcast_refresh()
  end

  def handle_action("delete", %{"id" => id, "actor" => actor}) do
    Sidecar.Beads.delete([id], actor)
    Sidecar.Beads.broadcast_refresh()
  end

  def handle_action("done", %{"id" => id, "actor" => actor}) do
    Sidecar.Beads.close(id, actor)
    Sidecar.Beads.broadcast_refresh()
  end
end
```

### `Sidecar.Beads` — HTTP client (new)

Not an `:exec.run` wrapper — see "Beads as dedicated Docker services" below for why. `Sidecar.Beads` is a `Req`-based HTTP client, the same pattern already used for Typesense/Searxng/Tika/agent-vault (`Sidecar.Typesense`, `sidecar/lib/sidecar/secrets/agent_vault.ex`), talking to the `beads` compose service over the internal Docker network:

Verified against `internal/httpapi/spec/openapi.v0.yaml` in the beads repo source (not served over HTTP — `bd serve --help`'s "(/v0)" refers to the API version, not a fetchable URL; the CLI's own `--help` output describes the CLI, not this contract). Every shape below is read from that file, not guessed:

```elixir
# planck_docker/sidecar/lib/sidecar/beads.ex
defmodule Sidecar.Beads do
  @topic "sidecar:widget:beads-board"

  @spec base_url() :: String.t()
  defp base_url, do: Sidecar.Config.beads_url!()  # e.g. "http://beads:8377"

  @spec list(keyword()) :: {:ok, map()} | {:error, term()}
  def list(params \\ []) do
    # GET /v0/beads/issues — status/limit/cursor/sort as query params.
    # Default excludes closed status; pass status: "closed" for the done list.
    # For the widget's board (open + in_progress columns), not for bd_ready
    # (see ready/1 below — a different endpoint with different semantics).
    get("/v0/beads/issues", params)
  end

  @spec ready(keyword()) :: {:ok, map()} | {:error, term()}
  def ready(params \\ []) do
    # GET /v0/beads/ready — a DIFFERENT endpoint from list/1 with status
    # filtering, not a parameter on it. Restricted to status=open AND no
    # unresolved blockers — an open-but-blocked issue would pass a naive
    # status=open filter on list/1 but never appears here. This is what
    # bd_ready (the LLM tool) should call, matching bd ready --json exactly.
    get("/v0/beads/ready", params)
  end

  @spec create(String.t(), String.t()) :: {:ok, map()} | {:error, term()}
  def create(title, actor) do
    # POST /v0/beads/issues — CreateIssueRequest: required [actor, title].
    # issue_type is technically optional in the schema but an omitted one is
    # refused by workspace validation on every shipped workspace — this is
    # exactly what tripped the unexplained 400 seen while testing. Always send it.
    post("/v0/beads/issues", %{title: title, actor: actor, issue_type: "task"})
  end

  @spec claim(String.t(), String.t()) :: {:ok, map()} | {:error, term()}
  def claim(id, actor) do
    # POST /v0/beads/issues/{id}:claim — ClaimRequest: {actor} ONLY.
    # additionalProperties: false, so a redundant "assignee" field (an earlier
    # draft of this sketch included one) would be refused outright as an
    # unknown body member. Real compare-and-set semantics server-side: 200
    # {already_claimed: true} on an idempotent re-claim by the same actor,
    # 409 {already_claimed, assignee: <holder>} if someone else holds it,
    # 409 {not_claimable, issue_status: ...} if it's not in a claimable state.
    # No client-side race guard needed — the server already does this properly.
    post("/v0/beads/issues/#{id}:claim", %{actor: actor})
  end

  @spec close(String.t(), String.t(), String.t() | nil) :: {:ok, map()} | {:error, term()}
  def close(id, actor, reason \\ nil) do
    # POST /v0/beads/issues/{id}:close — CloseIssueRequest: required [actor],
    # optional reason/session/force/expected_version. Idempotent re-close
    # (200, already_closed: true) writes neither reason nor session — first
    # close wins.
    post("/v0/beads/issues/#{id}:close", %{actor: actor, reason: reason})
  end

  @spec delete([String.t()], String.t() | nil) :: {:ok, map()} | {:error, term()}
  def delete(ids, actor \\ nil) when is_list(ids) do
    # POST /v0/beads/issues:delete — a collection-level custom method, NOT
    # DELETE /v0/beads/issues/{id} (an earlier draft of this sketch guessed
    # wrong). DeleteIssuesRequest: required [ids] (array, 1-1000), actor
    # optional. Refuses (400) if a named bead has a dependent outside the
    # request unless cascade/force is set — not needed for our single-id case.
    post("/v0/beads/issues:delete", %{ids: ids, actor: actor})
  end

  @doc """
  Re-renders the board and broadcasts it. Called after *any* mutation —
  by the widget's own handle_action/2 AND by every mutating tool
  (bd_claim/bd_create/bd_delete/bd_done) — since they run through a
  completely different path (execute_tool/4) than widget actions do.
  Without this on the tool side, an open board goes stale the moment
  another agent claims/creates/closes something, which defeats the point
  of a shared, watchable board.
  """
  @spec broadcast_refresh() :: :ok
  def broadcast_refresh do
    Phoenix.PubSub.broadcast(Planck.Agent.PubSub, @topic, {:widget_rendered, Sidecar.Widgets.Beads.render(nil)})
    :ok
  end

  # ---------------------------------------------------------------------------
  defp get(path, params), do: request(:get, path, nil, params: params)
  defp post(path, body), do: request(:post, path, body)

  defp request(method, path, body, opts \\ []) do
    headers = [{"authorization", "Bearer #{Sidecar.Config.beads_token!()}"}]
    case Req.request([method: method, url: base_url() <> path, json: body, headers: headers] ++ opts) do
      {:ok, %{status: s, body: body}} when s in 200..299 -> {:ok, body}
      {:ok, %{status: s, body: body}} -> {:error, {s, body}}
      {:error, reason} -> {:error, reason}
    end
  end
end
```

**One beads instance per Planck installation, shared by every agent and session** — not per-project, not per-session. Tasks here are meant as a structured way to hand work to workers (in place of a prompt), typically thrown away once done, not a long-lived per-project backlog — so there's no "which project does this session belong to" scoping to design.

### `Sidecar.Config` — new `beads_url` key

Same shape as the existing `typesense_url`/`searxng_url`/`tika_url` entries in `sidecar/lib/sidecar/config.ex` — a Skogsra `app_env` resolved from an env var the `planck` compose service passes in:

```elixir
@envdoc "Base URL of the beads HTTP API service (internal Docker service)."
app_env :beads_url, :sidecar, :beads_url,
  os_env: "BEADS_URL",

  os_env: "BEADS_TOKEN",
  default: nil
```

And in `planck_docker/compose.yml`'s `planck` service `environment:` block, alongside the existing `TYPESENSE_URL`/`SEARXNG_URL`/`TIKA_URL` lines:

```yaml
BEADS_URL: http://beads:8377
BEADS_TOKEN: ${BEADS_TOKEN}
```

(See "Beads as dedicated Docker services" below for why a token is required at all — `bd serve` needs `--allow-non-loopback` to accept connections from another container, which in turn requires one.)

The widget's own actions above are **unrestricted** — `handle_action/2` isn't gated by `TEAM.json` at all (that mechanism only governs what an *agent* can invoke as a tool call, see below). A human clicking in the sidebar/board gets create, delete, done, and claim-on-behalf-of any team member — the `assignee` for a human-initiated claim comes from a picker in the UI, not from the caller's own identity.

**Agent picker for "assign to":** sourced from the *live* registry (`Registry.lookup(Planck.Agent.Registry, {team_id, :member})`, the same source `list_team` already uses) — only agents actually running right now, not everyone configured in `TEAM.json`. If the team isn't started, there's nothing to assign to.

### Beads tool set (LLM-facing)

Five separate tools, not one tool with an action parameter — deliberate, so `TEAM.json`'s existing per-member `"tools"` list (see `AgentSpec.resolve_tools/2`, `planck_agent/lib/planck/agent/agent_spec.ex:265-278`) can restrict them individually.

| Tool | `Sidecar.Beads` call | Scope | Broadcasts refresh? |
|---|---|---|---|
| `bd_ready` | `ready()` — dedicated endpoint, not a `list/1` filter (see `Sidecar.Beads.ready/1`) | workers opt in via `TEAM.json` | no — read-only |
| `bd_done` | `close(id, actor)` | workers opt in via `TEAM.json` | **yes** |
| `bd_claim` | `claim(id, "<resolved id>")` | orchestrator (see below) | **yes** |
| `bd_create` | `create(title, actor)` | orchestrator (see below) | **yes** |
| `bd_delete` | `delete([id], actor)` | orchestrator (see below) | **yes** |

Every mutating tool calls `Sidecar.Beads.broadcast_refresh()` after its call, exactly like the widget's own actions do (see `Sidecar.Beads` above) — they run through `execute_tool/4`, a completely different path from `handle_action/2`, so without this an open board would go stale the moment another agent claims/creates/closes something instead of reflecting the team's actual live activity.

**No new `planck_agent` code needed for permissions.** `AgentSpec.resolve_tools/2` already resolves an empty `spec.tools` (the common case for an orchestrator, which doesn't normally declare a restrictive list) to the *entire* tool pool — so as long as all five tools are registered sidecar tools, the orchestrator gets all of them automatically, in any team shape (static or dynamic), with no config or code change. Workers only get `bd_ready`/`bd_done` if they explicitly list those two names in their own `TEAM.json` `"tools"` array.

**`bd_claim`'s identity resolution** — the LLM never supplies who's claiming; the tool resolves it server-side from the runtime-provided `agent_id`, the same way `Sidecar.Tools.UpdateMemory.resolve_agent_info/1` already does, since `agent_id` itself is `:crypto.strong_rand_bytes(8)` regenerated on every restart (`agent_spec.ex:390-393`) — not durable. `team_name`/`name` (straight from `TEAM.json`, re-read every boot) are the durable pair:

```elixir
execute_fn: fn agent_id, _id, %{"issue_id" => issue_id} ->
  {:ok, pid} = Planck.Agent.whereis(agent_id)
  state = Planck.Agent.get_state(pid)
  assignee = "#{state.team_name}:#{state.name}"
  result = Sidecar.Beads.claim(issue_id, assignee)
  Sidecar.Beads.broadcast_refresh()
  result
end
```

### `Planck.Web.Live.SidecarWidget` — generic LiveComponent (new, `planck_cli`)

This is the one place that decides the opaque term is HTML — that assumption belongs here, not upstream in `planck_agent`/`planck_headless`.

**Three real bugs found during Phase 3 implementation, not just style fixes — the original sketch (kept below for history) doesn't work as written:**

1. **`Phoenix.LiveComponent` has no `handle_info/2`.** Confirmed by the compiler, not a style opinion: a component has no process of its own, so a message a component's `Phoenix.PubSub.subscribe/2` call causes to be delivered arrives at the *parent* LiveView's `handle_info/2` — never at anything defined on the component module. The parent must route it in with `send_update/3`. The component's own reaction has to be a second `update/2` clause, not `handle_info/2`.
2. **`Phoenix.PubSub.subscribe/2` is not idempotent — confirmed empirically**, not assumed: subscribing the same pid N times to the same topic delivers N copies of every broadcast. Since `update/2` reruns on every parent re-render (not just first mount), the sketch below would leak duplicate subscriptions — and would also needlessly repeat the RPC pull on every unrelated parent render, contradicting the "pull once, then push" design.
3. **`Phoenix.LiveComponent` also has no termination callback.** Checked directly (`Phoenix.LiveComponent.behaviour_info(:callbacks)` lists only `update_many/1, update/2, mount/1, render/1, handle_event/3, handle_async/3`), while chasing "how does the component unsubscribe when the modal closes." It can't — there's no hook. Combined with bug 1, this means the component must never subscribe at all: subscribe/unsubscribe moves entirely to the *owning LiveView*, tied to its own explicit open/close event handlers (a LiveView has a real process and real lifecycle control), not to the component's mount/unmount. This also resolves open question 1 below ("Widget lifecycle / cleanup") for the generic case, not just beads.

Corrected — `SidecarWidget` itself now only pulls and receives pushes, no PubSub of its own:

```elixir
defmodule Planck.Web.Live.SidecarWidget do
  use Planck.Web, :live_component

  # The parent re-passes widget_id on every one of its own re-renders, not
  # just first mount, so this guards against re-issuing the RPC pull (and
  # clobbering html pushed since via send_update) on every unrelated parent
  # render.
  def update(%{widget_id: id}, %{assigns: %{widget_id: id}} = socket) do
    {:ok, socket}
  end

  def update(%{widget_id: id}, socket) when is_binary(id) do
    socket =
      case Planck.Headless.Widgets.render(id, socket.assigns.myself) do
        {:ok, html} -> assign(socket, html: html, error: nil)
        {:error, reason} -> assign(socket, html: nil, error: reason)
      end

    {:ok, assign(socket, :widget_id, id)}
  end

  # Forwarded by the owning LiveView's own handle_info/2 via
  # send_update(SidecarWidget, id: "sidecar-widget-modal", html: new_html) —
  # see bugs 1 and 3 above. This LiveView is Phase 6/7's job, not this phase's.
  def update(%{html: html}, socket), do: {:ok, assign(socket, html: html, error: nil)}

  def update(_assigns, socket), do: {:ok, socket}

  def handle_event("widget_action", params, socket) do
    case Planck.Headless.Widgets.dispatch_action(socket.assigns.widget_id, params["action"], params["args"]) do
      :ok -> LiveToast.send_toast(socket, :info, "#{params["action"]} succeeded")
      {:error, reason} -> LiveToast.send_toast(socket, :error, "#{params["action"]} failed: #{inspect(reason)}")
    end

    {:noreply, socket}
  end

  def render(%{error: :sidecar_not_connected} = assigns) do
    ~H"""
    <div id={"widget-#{@widget_id}"} class="text-muted-foreground text-xs">
      Sidecar not connected — this widget will reload once it reconnects.
    </div>
    """
  end

  def render(assigns) do
    ~H"""
    <div id={"widget-#{@widget_id}"}><%= Phoenix.HTML.raw(@html) %></div>
    """
  end
end
```

`Phoenix.HTML.raw/1`, not bare `raw/1` — confirmed this codebase never imports `Phoenix.HTML` into `live_component`/`live_view` (only into the `html` macro), so every existing call site uses the qualified name (`chat_component.ex`'s `render_markdown/1`, for one). Bare `raw/1` doesn't compile here.

### One modal, not a registry — where subscribe/unsubscribe actually lives

`planck_cli` has no compile-time knowledge of widget ids (sidecars, including future custom ones, define their own), so rather than a dynamic component registry keyed by widget id, the WebUI hosts a single, fixed-id `SidecarWidget` instance — mirroring `Planck.Web.Live.SetupModal`'s existing pattern — re-targeted at whichever `widget_id` is currently open. This is what Phase 6/7's owning LiveView (`SessionLive`) needs to implement:

```elixir
def handle_event("open_widget", %{"widget_id" => id}, socket) do
  Phoenix.PubSub.subscribe(Planck.Agent.PubSub, "sidecar:widget:#{id}")
  {:noreply, assign(socket, :open_widget_id, id)}
end

def handle_event("close_widget", _params, socket) do
  if id = socket.assigns.open_widget_id do
    Phoenix.PubSub.unsubscribe(Planck.Agent.PubSub, "sidecar:widget:#{id}")
  end

  {:noreply, assign(socket, :open_widget_id, nil)}
end

def handle_info({:widget_rendered, id, html}, socket) do
  send_update(Planck.Web.Live.SidecarWidget, id: "sidecar-widget-modal", html: html)
  {:noreply, socket}
end
```

The broadcast payload names the widget (`{:widget_rendered, id, html}`, not just `{:widget_rendered, html}`) — routing correctness depends on that, not on the component id, since the component id is always `"sidecar-widget-modal"` regardless of which widget is currently shown.

### Container type — modal only, for now

A widget gets `:modal` for free via `use Planck.Agent.Widget` (see the design decisions above) and overrides `container/0` to opt into something else once a second kind exists. `SessionLive`'s `open_widget` handler fetches it once via `Planck.Headless.Widgets.container/1` before mounting `SidecarWidget`, since the wrapping chrome (a modal's dialog markup vs. a drawer's slide-out markup) is a decision the *host* template makes, not something `SidecarWidget`'s own `render/1` can express — different container kinds need different surrounding markup, not just different content. As of this version only `:modal` has real chrome; `:drawer`/`:fullscreen` are recognized values with no renderer yet (falls back to modal chrome, logged, until one is built).

The `LiveToast.send_toast/3` call above is still Phase 14 work — the actual Phase 3 implementation deliberately omits it (dispatches the action and returns `{:noreply, socket}` with a comment noting the deferral), since `live_toast` isn't a dependency yet. This sketch shows the eventual end state, not what phase 3 alone produces.

Previously, a bare `{:ok, html} = Planck.Headless.Widgets.render(...)` match here would raise a `MatchError` and crash the LiveView if the sidecar was down — `Planck.Headless.Widgets.render/2` already correctly returns `{:error, :sidecar_not_connected}` (mirroring `Secrets`'s dispatch), the consumer just never branched on it. Fixed above; no change needed to the RPC layer itself.

### New dependencies

`planck_docker/sidecar/mix.exs` needs `{:phoenix_live_view, "~> ..."}` (for `Phoenix.Component`/`~H`). This does **not** require an Endpoint, Router, or Cowboy — the sidecar stays a plain OTP app, only gaining the template-compiling macros.

`planck_cli/mix.exs` needs `{:live_toast, "~> ..."}`, for widget action feedback (see `SidecarWidget.handle_event/3` above). ### Beads as dedicated Docker services

Not installed into the main `planck` image at all — beads runs as two new services in `planck_docker/compose.yml`, matching the existing `typesense`/`searxng`/`tika`/`vault` convention (one process, one purpose, per service; Docker's own container lifecycle handles supervision, no new Elixir-side process-management code needed).

**Two separate pieces of persistent state, not one — verified, not assumed.** Tested restarting a `bd init --server` client against an already-populated dolt server after deleting its local `.beads/` control directory: it fails hard with `PROJECT IDENTITY MISMATCH` (the local `metadata.json`'s project id no longer matches the one recorded in the database) rather than cleanly reconnecting. So the `bd` client's own `.beads/` directory (project identity + config, separate from dolt's actual SQL data) has to survive `beads` container restarts just as much as dolt's data has to survive `dolt` container restarts — one volume each, named after the service that owns it (matching the existing `typesense`↔`typesense-data`, `vault`↔`vault-data` convention):

```yaml
dolt:

    - ${PLANCK_HOME}/dolt-data:/data
  command: ["sql-server", "--host", "0.0.0.0", "--port", "3306"]
  healthcheck:
    test: ["CMD", "dolt", "sql-client", "--host", "127.0.0.1", "--port", "3306", "-q", "SELECT 1"]
    interval: 5s
    retries: 10
  restart: unless-stopped

beads:
  build:
    context: ..
    dockerfile: planck_docker/beads/Dockerfile
  volumes:
    - ${PLANCK_HOME}/beads-data:/data/.beads
  environment:
    BEADS_TOKEN: ${BEADS_TOKEN}
  depends_on:
    dolt:
      condition: service_healthy   # not service_started — bd init --server would otherwise race dolt's own boot
  restart: unless-stopped
```

And in the `planck` service, alongside the existing `depends_on` entries and `BEADS_URL`:

```yaml
depends_on:

    condition: service_started

  BEADS_TOKEN: ${BEADS_TOKEN}
```

`dolthub/dolt` is an official, actively-maintained image on Docker Hub, and `2.2.0` is a real published tag — confirmed via the registry API, not assumed. No custom Dockerfile needed for the SQL server side at all.

**`planck_docker/beads/Dockerfile` + entrypoint (new).** Installs the `bd` binary (pinned version). The entrypoint has to check for an existing `.beads/config.yaml` before calling `bd init` at all — confirmed empirically that `bd init --server` is **not** idempotent on its own (a second call against an already-initialized workspace exits 1 with `"This workspace is already initialized"`):

```sh
#!/bin/sh
set -e
mkdir -p /data/.beads
export BEADS_DIR=/data/.beads
if [ ! -f "$BEADS_DIR/config.yaml" ]; then
  bd init --server --server-host dolt --server-port 3306 --quiet --skip-agents
fi
echo "$BEADS_TOKEN" > /run/beads-token
exec bd serve --addr 0.0.0.0:8377 --allow-non-loopback --allowed-host beads --auth-token-file /run/beads-token
```

**Auth — the other real blocker this design missed at first.** `bd serve --help`, read carefully rather than skimmed: *"The DNS-rebinding check answers only to loopback spellings and the bind address, so a client dialing a service name gets 400 on every request; enumerate the names it dials with `--allowed-host`"* — exactly what `Sidecar.Beads` does, dialing `http://beads:8377`. And separately, *"`--allow-non-loopback` REQUIRES a token file"* — traffic arriving over the Docker bridge network from the `planck` container isn't loopback traffic from `bd serve`'s point of view, even though it's internal to the stack. Without `--allow-non-loopback --allowed-host beads --auth-token-file`, every single call from the sidecar would 400. `BEADS_TOKEN` is one shared secret (generated once, same pattern as `TYPESENSE_API_KEY` — no bootstrap round-trip needed, unlike `AGENT_VAULT_TOKEN`'s setup-container dance), passed to both services and written to `Authorization: Bearer <token>` by `Sidecar.Beads`'s request helper (update needed there — not shown above, add a `headers:` entry to `request/4` reading `Sidecar.Config.beads_token!()`).

**Install scripts need the same directory-creation update `typesense-data` already has, for both new volumes:**
- `docs/install_docker.sh:61` — add `"$PLANCK_HOME/dolt-data"` and `"$PLANCK_HOME/beads-data"` to the `mkdir -p` list.
- `docs/install_docker.ps1:61` — add `"dolt-data"` and `"beads-data"` to the `foreach ($dir in ...)` list.
- `dev_docker.sh:37` — add `"$DEV_DIR/dolt-data"` and `"$DEV_DIR/beads-data"` to its `mkdir -p` list.
- `BEADS_TOKEN` needs the same random-value generation as `SEARXNG_SECRET`/`TYPESENSE_API_KEY` in all three scripts' `.env`-writing sections.

**Consequence worth noting:** since beads' actual data now lives in the `dolt`/`beads` services' own volumes, not the workspace bind-mount, there's no `.beads/` directory inside `/workspace` at all — the Typesense-exclusion fix from earlier in this design pass (adding `.beads` to `Sidecar.Watcher`'s `@excluded_dirs`) is now unnecessary. Nothing to exclude.

## 2. `{:custom, :ui}` Messages

### Problem

A tool's result is plain text sent straight to the LLM (`Planck.Agent.MessageBuilder.build_tool_result/1` requires `{:ok, string} | {:error, term}`). There's currently no way for a tool to also attach a UI affordance — e.g. "open the widget you just updated" — without either polluting the model's context with UI-only data, or hand-rolling per-tool special cases in the LLM-facing serializer.

### Design decision

Reuse the existing `{:custom, atom()}` message-role convention, already documented in `Planck.Agent.Message` (`planck_agent/lib/planck/agent/message.ex:6-7`) and already used for `{:custom, :summary}` (checkpoints) and `{:custom, :agent_response}` (inter-agent replies). `Message.to_ai_messages/1` already has a catch-all that drops any unrecognized custom role before the context reaches the LLM:

```elixir
%__MODULE__{role: {:custom, _}} -> []
```

So `{:custom, :ui}` gets "invisible to the model" for free. **No changes to `planck_ai`'s adapter are needed.**

### Tool result contract

A tool's `execute_fn` may return a 3-element form instead of the normal 2-element one:

```elixir
{:ok, text}                          # unchanged — existing tools keep working as-is
{:ok, text, ui: %{widget: widget_id, data: initial_snapshot}}   # new — opts into a UI side effect
{:error, reason}                     # unchanged
```

### Implementation

`finish_tool_execution/2` (`planck_agent/lib/planck/agent.ex:681`) strips the `ui:` element before building the plain tool-result message, then persists a sibling `{:custom, :ui}` message for any result that carried one:

```elixir
defp finish_tool_execution(results, state) do
  results = Enum.reverse(results)

  tool_result_msg =
    results
    |> Enum.map(fn {id, result} -> {id, strip_ui(result)} end)
    |> MessageBuilder.build_tool_result()
    |> then(&persist_message(state, &1))

  ui_msgs =
    for {id, {:ok, _text, ui: payload}} <- results do
      Message.new({:custom, :ui}, [{:ui, id, payload}]) |> then(&persist_message(state, &1))
    end

  %{state | messages: state.messages ++ [tool_result_msg | ui_msgs], status: :streaming}
end

defp strip_ui({:ok, text, ui: _}), do: {:ok, text}
defp strip_ui(result), do: result
```

`MessageBuilder.build_tool_result/1` is **unchanged** — it never sees the `ui:` element, so its truncation and `is_binary`/`inspect` handling stays exactly as it is today.

### Display

`Planck.Web.Live.ChatEntries.classify_row/4` (`planck_cli/lib/planck/web/live/chat_entries.ex:353-401`) gains a clause parallel to the existing `{:custom, :summary}` / `{:custom, :agent_response}` handling:

```elixir
{:custom, :ui} ->
  for {:ui, tool_id, payload} <- msg.content do
    %{
      id: "ui-#{tool_id}",
      type: :ui_widget,
      side: :left,
      author: author,
      widget: payload.widget,
      widget_data: payload.data,
      timestamp: msg.timestamp
    }
  end
```

The chat template renders a button for `:ui_widget` entries; clicking it mounts `Planck.Web.Live.SidecarWidget`, seeded with `widget_data` from the tool call (no extra RPC round-trip needed to open it — the widget only needs to make its own RPC/PubSub calls for anything *after* that first paint).

**`Planck.Web.Live.SessionLive` (the chat page) has to implement the subscribe/forward contract `SidecarWidget`'s moduledoc documents but doesn't implement itself** — see Section 1's "One modal, not a registry" subsection: `SidecarWidget` never touches `Phoenix.PubSub` (no `handle_info/2` to receive on, no termination hook to unsubscribe from), so `SessionLive` owns the full lifecycle, tied to its own explicit open/close actions, not to mounting/unmounting the component:

```elixir
# planck_cli/lib/planck/web/live/session_live.ex
def handle_event("open_widget", %{"widget_id" => id}, socket) do
  Phoenix.PubSub.subscribe(Planck.Agent.PubSub, "sidecar:widget:#{id}")
  {:noreply, assign(socket, :open_widget_id, id)}
end

def handle_event("close_widget", _params, socket) do
  if id = socket.assigns.open_widget_id do
    Phoenix.PubSub.unsubscribe(Planck.Agent.PubSub, "sidecar:widget:#{id}")
  end

  {:noreply, assign(socket, :open_widget_id, nil)}
end

def handle_info({:widget_rendered, id, html}, socket) do
  send_update(Planck.Web.Live.SidecarWidget, id: "sidecar-widget-modal", html: html)
  {:noreply, socket}
end
```

The mounted component always uses the fixed id `"sidecar-widget-modal"` (one modal, re-targeted at whichever widget is open — not a registry keyed by widget id), and clicking a `:ui_widget` chat entry's button fires `"open_widget"` with that entry's `widget` value rather than mounting the component directly from the template. Without this, mounting the widget from chat would show its first paint correctly and then never update again — silently, no error, exactly the kind of gap Phase 15's "confirm each live-updates via PubSub" verification step is meant to catch, so it has to land in the same phase as the mount itself, not later.

### New `entry_type`

`:ui_widget` is added to `Planck.Web.Live.ChatEntries.entry_type/0`, with `:widget` and `:widget_data` as its associated optional keys.

### Proof of concept: beads

The deliverable for this version. `bd_ready` (Section 1) is the trigger: its `execute_fn` returns the 3-element form, naming the widget without duplicating its data:

```elixir
{:ok, format_ready_beads(), ui: %{widget: "beads-board", data: nil}}
```

`finish_tool_execution/2` strips the `ui:` element for the LLM-facing tool result exactly as described above, and persists a sibling `{:custom, :ui}` message carrying `%{widget: "beads-board", data: nil}`. `ChatEntries` renders a button; clicking it mounts `Planck.Web.Live.SidecarWidget` (Section 1) with `widget_id: "beads-board"`, which does its own RPC pull (`Planck.Headless.Widgets.render/2`) for the first paint and then lives off the `"sidecar:widget:beads-board"` PubSub topic — no data needed to have arrived with the tool result.

**Not in this version:** `write_skill` adopting the `ui:` contract. An earlier draft of this spec had it as the proof of concept, including a required fix to `Sidecar.SkillReflector.Runner`'s `:tool_end` pattern match (`planck_docker/sidecar/lib/sidecar/skill_reflector/runner.ex:87`, which matches the raw 2-tuple result and would silently stop firing against the new 3-tuple form). That fix is still correct whenever `write_skill` does adopt this contract — just not now.

### Replace `Earmark` with `MDEx`

`Earmark` is unmaintained (confirmed by prior experience replacing it in another project for the same reason — not a currency issue; `1.4.49` is up to date against its own `~> 1.4` requirement). Replacement: [`mdex`](https://hex.pm/packages/mdex) (`~> 0.13`), a Rust/`comrak`-backed renderer via Rustler.

```elixir
# planck_cli/lib/planck/web/live/chat_component.ex:318
def render_markdown(text) when is_binary(text) do
  case MDEx.to_html(text) do
    {:ok, html} -> Phoenix.HTML.raw(html)
    _ -> Phoenix.HTML.html_escape(text)
  end
end
```

**Safety requirement, not optional:** the current `Earmark.as_html(text, escape: true, ...)` escapes raw HTML embedded in the markdown source before rendering it — load-bearing, since this text can be agent- or tool-authored (skill bodies, tool results) and reaches the chat DOM. MDEx's default behavior already matches this — raw HTML passthrough only happens if `render: [unsafe: true]` is explicitly set, which this migration must **not** set. If sanitization beyond that default is wanted, MDEx exposes it via `sanitize:` (backed by the `ammonia` crate) or the standalone `MDEx.safe_html/2`, but the default (unsafe not set) is the equivalent of today's `escape: true` and should be the target behavior, not an enhancement to design in.

Also confirm `:extension` options needed to match Earmark's current feature set (`breaks: true` — MDEx's `extension: [hardbreaks: ...]` or equivalent; GFM tables/autolinks if any existing chat content relies on them) before swapping, since the two libraries' CommonMark extension sets aren't identical.

## Open design questions for review

1. ~~Widget lifecycle / cleanup~~ **Resolved, generically, not just for beads.** `Phoenix.LiveComponent` has no termination callback at all (checked directly — `terminate/2` isn't in `behaviour_info(:callbacks)`), so there's no hook to unsubscribe from on unmount regardless of what a given widget does in the background. Fix: `SidecarWidget` never subscribes to PubSub itself; the owning LiveView's own explicit `open_widget`/`close_widget` event handlers own the subscribe/unsubscribe lifecycle (see Section 1, "One modal, not a registry").
2. ~~Multiple simultaneous widget instances~~ **Resolved** — one beads DB per Planck installation means every open widget is necessarily showing the same data, so sharing one subscription per `id` isn't a design choice, it's the only correct behavior. Confirmed, not just assumed.
3. ~~Error handling~~ **Resolved** — `SidecarWidget.update/2` previously did a bare `{:ok, html} = ...` match that would crash on `{:error, :sidecar_not_connected}`; fixed to branch on both and render a "sidecar not connected" state (see Section 1).
4. ~~External mutation staleness~~ **Mostly resolved, and the remaining gap shrank further.** The actual risk wasn't external `bd` CLI usage, it was the four mutating *tools* (`bd_claim`/`bd_create`/`bd_delete`/`bd_done`) running through `execute_tool/4`, a separate path from the widget's own `handle_action/2`, and not broadcasting a refresh. Fixed: `Sidecar.Beads.broadcast_refresh/0` is shared and called by both. Now that beads lives in its own `dolt`/`beads` services rather than the workspace filesystem, "someone shelling into the container and running `bd` directly" isn't really possible anymore — there's no `.beads/` to reach from inside the `planck` container at all, only the HTTP API. The `file_system`-watcher idea is accordingly dropped; if true push-based external-mutation detection is ever wanted, `bd serve`'s own `events.watch`/`events.list` capability (discovered but not explored — see Section 1) is the path, not a filesystem watcher.
5. ~~Flash/toast support~~ **Resolved** — adopting `live_toast` (`planck_cli`-only dependency; the sidecar never touches a `Socket`/`Conn` so it needs none) instead of vanilla flash, specifically because `send_toast/3` works from a `LiveComponent`'s `handle_event/3` without the parent-propagation workaround the spike would have otherwise required.
