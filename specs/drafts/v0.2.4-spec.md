# Planck v0.2.4 — Spec

## Scope

Adds a second model family alongside the existing chat/agent models: **RLCD**
("Reinforcement Learning for Calibrated Decisions") models, exemplified by
Typesafe AI's Jev and wire-compatible self-hosted servers (e.g. `decider`).
These models don't do chat or tool-calling — they take a state and a set of
typed questions (Choice / Score / Noul) and return calibrated probabilities in
a single forward pass. `req_llm` (vendored under `planck_ai/deps/req_llm`)
already ships `ReqLLM.Providers.TypeSafe` (id `:typesafe`, `POST
/v1/systemone`, `ReqLLM.Evaluation.evaluate/4`) and speaks this wire format —
that provider is complete and out of scope here. What's missing is everything
above it: `Planck.AI.Model` has no way to say "this is an RLCD model, not an
LLM," `list_models` can't surface that distinction to an agent, there's no
`classify` tool that calls `ReqLLM.evaluate/4`, and there's no config/UI path
for configuring a `:typesafe` provider (cloud or self-hosted).

In scope:

1. A `type: :llm | :rlcd` field on `Planck.AI.Model`.
2. A `:typesafe` provider in `planck_ai`, cloud and self-hosted-compatible
   (mirrors the existing `:openai` / OpenAI-compatible split).
3. A `Planck.AI.evaluate/4` public API and `Planck.AI.ReqLLMBehaviour`
   extension so `Adapter`/Mox testing covers evaluation the same way it
   covers chat.
4. A `classify` tool, gated on at least one configured `:rlcd` model,
   available to every agent (orchestrator and worker) the same way
   `list_team`/`call_agent` are — not a sidecar tool requiring `TEAM.json`
   opt-in.
5. `list_models` surfacing `type` per model.
6. Setup-modal support for adding a Typesafe / Typesafe-compatible provider
   and model.

## Use Cases

- An orchestrator triages an inbound request ("is this a refund, a bug
  report, or spam?") with a `choice` question against a self-hosted `decider`
  model before spawning the specialist worker for the winning category —
  cheaper and lower-latency than asking a chat model to reason it out in
  prose and parse the answer back out.
- A worker about to take a destructive or irreversible action (delete,
  refund, escalate) runs a `boolean` question first ("does the user's message
  clearly authorize this?") and uses the returned probability as a confidence
  gate, instead of trusting its own free-text judgment.
- A large team with many workers uses `classify` for high-volume routing
  decisions without spending chat-model tokens (or latency) on each one.
- A self-hosted setup (no cloud LLM budget for classification-shaped work)
  points `:typesafe`'s `base_url` at a local `decider` instance the same way
  `:openai`'s `base_url` already points at a local llama.cpp/Ollama instance.

## Explicitly not touched

- **`decider` as a bundled sidecar service.** Already decided in discussion
  preceding this spec — self-hosting it is the user's own AI-server
  concern, not something `planck_docker` packages.
- **SemIf / OpenJev.** A disclaimed, unaffiliated browser experiment with no
  server API (client-side logit readout via `wllama`) — nothing to
  integrate as a provider.
- **Modeling Choice/Score/Noul as typed structs in `planck_ai`.** The
  `questions`/`object` maps pass through opaquely between `classify`'s tool
  args and `ReqLLM.evaluate/4` — no Planck-level schema validation beyond
  the tool's own JSON parameter schema. Revisit only if a second RLCD
  provider shows up with an incompatible question-type vocabulary.
- **`req_llm`'s `ReqLLM.Providers.TypeSafe` itself.** Already complete
  upstream; not modified by this spec.

   endpoint?~~ **Resolved.** Yes, cloud: `GET /v1/models`. `decider`
   doesn't implement it — self-hosted/compatible servers degrade
   gracefully. See [Phase 1](v0.2.4-spec/phase-1-planck-ai.md)'s Pre-work.
2. ~~Confirmed field names for `choice`/`score`/`boolean` question types.~~
   **Resolved.** All three use `criteria` (object for choice, array for
   score, optional `true`/`false`-keyed object for boolean/noul) — see
   [Phase 1](v0.2.4-spec/phase-1-planck-ai.md)'s Pre-work and
   [Phase 2](v0.2.4-spec/phase-2-planck-agent.md)'s corrected
   `@classify_schema`.
3. ~~Whether the setup modal's model sub-step needs a manual-entry
   fallback for providers without discovery, or already has one.~~
   **Resolved.** The fallback already exists and is generic
   (`@models != []` ? dropdown : free-text input) — `decider` returning
   `[]` lands in the same path Ollama/llama.cpp already hit. What actually
   needs wiring is upstream: `load_models/1` needs `:typesafe` added to its
   cloud-provider guard, and `fetch_local_models/1` needs to become
   provider-aware instead of hardcoding `:openai`. See
   [Phase 4](v0.2.4-spec/phase-4-planck-cli.md).
