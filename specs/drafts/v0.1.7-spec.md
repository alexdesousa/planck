# Planck v0.1.7 — Release Spec

## Overview

Per-agent persistent memory for fixed teams and a skill system overhaul with
self-improvement. Agents declared in TEAM.json can carry a `memory:` field; at
session start the file is injected as a frozen snapshot into the system prompt and
a `memory` built-in tool lets the agent maintain it across sessions. Long-term
recall is available via `session_search` over the existing SQLite history.

The skill index gains frontmatter-driven pinning, usage tracking via `load_skill`,
and a Layer 1 self-improvement loop — agents write new skills after complex
repeatable workflows. The `## Planck guides` section moves out of the default
system prompt and into a bundled `planck_setup` skill, loaded on demand.

Dynamic workers (spawned via `spawn_agent`) are unaffected — they remain
purely task-scoped and ephemeral.

## Phase 1 — Short-term memory (`planck_agent`)

### TEAM.json — new `memory` field

Each member entry in TEAM.json may declare a `memory` path:

```json
{
  "type":          "orchestrator",
  "system_prompt": "orchestrator.md",
  "memory":        "memory.md"
}
```

The path is resolved relative to the team directory (same convention as
`system_prompt`). If the file does not exist it is created empty on first write.
Memory is per-agent-name, not per-agent-id — it persists across sessions for the
same named agent.

### `AgentSpec` changes

- New optional field: `memory_path: String.t() | nil` (default `nil`)
- `AgentSpec.from_map/2` parses `"memory"` from the TEAM.json entry and resolves
  it relative to `base_dir:`, the same way `system_prompt` file paths are resolved
- `AgentSpec.to_start_opts/2` passes `memory_path` through to the agent start opts

### `memory` built-in tool

New tool in `Planck.Agent.BuiltinTools`:

```
memory(action, entry)
```

- `action`: `"add"` | `"replace"` | `"remove"`
- `entry`: the text to add, the new text (for replace), or a substring to match
  for removal

**Behaviour:**
- Hard limit: 2 200 characters. If an `add` would exceed the limit the tool
  returns an error asking the agent to consolidate first.
- `replace` matches by substring of existing entry text.
- `remove` matches by substring and deletes the matching entry.
- Writes to disk immediately; changes are visible in the next session's frozen
  snapshot, not the current one.
- No-ops silently on agents without a `memory_path`.

### Frozen snapshot — storage and lifecycle

Memory lives in the agent's GenServer state as two new fields on `Planck.Agent`:

```elixir
memory_path:    Path.t() | nil   # path to the MEMORY.md file on disk
memory_content: String.t()       # the loaded snapshot; "" when no memory declared
```

**At `init`:** if `memory_path` is set, read the file from disk (empty string if it
does not exist yet) and store it in `memory_content`.

**On every LLM turn:** `build_system_prompt/1` prepends `memory_content` as a
`## Memory` section alongside the existing fields (`system_prompt`, skills, tools).
Because `memory_content` is held in state and nothing mutates it mid-session, the
system prompt is identical across all turns — prefix caching stays warm.

**On compaction:** `apply_compact/1` reloads `memory_content` from `memory_path`
after the message list is compacted, then stores it in the new state. The next turn
after compaction sees the refreshed snapshot. Since compaction already busts the
prefix cache, the reload is free.

**On server restart + resume:** `resume_session` calls `materialize_team`, which
starts a fresh agent via `init`. The agent reads `memory_content` from disk at
that point, picking up any writes from the previous session. Restart + resume is
indistinguishable from a clean session start. If the server crashed mid-session
after a memory write but before all turns were persisted to SQLite, the memory on
disk may be slightly ahead of the message history — the agent will "remember"
something not in its conversation history. This is acceptable; an
over-informed agent is preferable to an under-informed one.

Memory is never sent to the compactor. `Compactor.build` operates on the
`messages` list only; the system prompt (and the memory snapshot within it) is
never passed to the compaction LLM call. Memory is not summarized — only refreshed.

### Memory management instructions

When `memory_path` is non-nil, inject a memory management section into the system
prompt automatically — the same pattern used for inter-agent tool guidance today
(`Tools.prepend_agents_md`). The injected text covers:

- What belongs in memory: durable facts, user preferences, environment details,
  project conventions, tool quirks, lessons learned
- What does not belong: session-specific notes, easily re-discovered facts, raw
  data dumps, information already in context files
- The 2 200-character hard limit and the consolidation expectation when full
- Save proactively — do not wait to be asked

## Phase 2 — Long-term recall (`planck_agent`)

### `session_search` built-in tool

Queries the SQLite message history across all past sessions for the current agent:

```
session_search(query)
```

Returns the most relevant excerpts (full-text search, ~20 ms). The agent uses this
to recall past context before asking the user to repeat themselves.

Only injected when `memory_path` is set (same condition as the `memory` tool).
Without memory declared in TEAM.json, the agent has no recall tools at all —
no behavior change for existing teams.

### Storage

Reuses the existing `Planck.Agent.Session` SQLite infrastructure. Queries filter
by both `team_alias` and `agent_name` — the combination is the stable identity
for an agent across sessions. Filtering by name alone is insufficient since
different teams can have agents with the same name (e.g. two "orchestrator"
agents in different teams).

## Phase 3 — Headless wiring (`planck_headless`)

- `SidecarManager` and `ResourceStore`: no changes needed
- `materialize_team` and `start_orchestrator` / `start_workers`: pass
  `memory_path` from `AgentSpec` through to agent start opts
- `builtins/0` remains unchanged — `memory` and `session_search` are only added
  to the tool pool when `memory_path` is non-nil (conditional injection, not
  global)

## Phase 4 — Skill system overhaul (`planck_agent`, `planck_headless`)

### Frontmatter-driven skill index

Skills gain two new optional frontmatter keys:

```markdown
---
name: my-skill
description: Does something useful.
always_present: false
planck_version: null
use_count: 0
last_used: null
---
```

- `always_present` (default `false`) — when `true`, the skill is always included
  in the frozen system prompt index regardless of usage. Intended for
  user-curated skills. Agent-created skills must not set this.
- `planck_version` — set by Planck on bundled skills. Used by the upgrade logic
  to detect stale content. `null` on user/agent-created skills.
- `use_count` / `last_used` — updated by `load_skill` on every call.

### Skill index assembly

At session start the system prompt skill index is built as three parts:

1. **Pinned** — all skills with `always_present: true`, always included, listed
   under `## Skills`
2. **Last used skills** — up to 5 skills without `always_present`, sorted by
   `last_used` then `use_count`, listed under `## Last used skills`
3. **Discovery line** — a single sentence appended after both sections:
   *"Call `list_skills` to discover more skills."*

The default of 5 for the "last used" section may be overridden per-team via a
future config key; 5 is sufficient for ~100-150 tokens of index overhead.

Example system prompt section:

```
## Skills

- **git-workflow**: Branching, commit, and PR conventions for this repo.

## Last used skills

- **elixir-dev**: Elixir/Mix project conventions, test patterns, and credo config.
- **planck-setup**: Guides for configuring Planck — providers, models, teams, skills, sidecars, and the HTTP API.

Call `list_skills` to discover more skills.
```

The index is frozen for the session. New skills created mid-session are not added
to the frozen index but are immediately discoverable via `list_skills` (which reads
from disk live) and loadable via `load_skill`.

At compaction the index is rebuilt from disk alongside memory — new skills created
during the session appear in the frozen index for the remainder of the session.

### `load_skill` tracking

`load_skill` updates `use_count` and `last_used` in the skill's frontmatter on
every call. This is the sole mechanism driving the "top N recently used" index.

### `write_skill` built-in tool

New tool in `Planck.Agent.BuiltinTools`:

```
write_skill(name, description, content, scope)
```

- `name`: kebab-case skill name (e.g. `"git-workflow"`)
- `description`: one-line description for the frontmatter and index (≤ 500 chars)
- `content`: markdown body — everything after the frontmatter block
- `scope`: `"project"` (`.planck/skills/<name>/SKILL.md`) or `"global"`
  (`~/.planck/skills/<name>/SKILL.md`); defaults to `"project"`

**Behaviour:**
- Assembles the full `SKILL.md` file including frontmatter. The agent supplies
  only the three semantic fields; the tool owns the shape:

  ```markdown
  ---
  name: <name>
  description: <description>
  always_present: false
  planck_version: null
  use_count: 0
  last_used: null
  ---

  <content>
  ```

- `always_present` and `planck_version` are always written as `false` and `null`
  respectively — agents may not set them.
- Creates the skill directory if it does not exist.
- If a `SKILL.md` already exists at the target path, overwrites the body and
  `description` while preserving all other frontmatter keys (including any
  user-set `always_present: true` and existing `use_count` / `last_used`).

### Self-improvement loop (Layer 1 only)

When `skill_pool` is non-empty, inject skill creation instructions into the system
prompt alongside existing skill guidance:

- After completing a complex, repeatable workflow (typically 5+ tool calls),
  evaluate whether the procedure is worth capturing as a skill.
- If yes, call `list_skills` first — check that no skill with the same name or
  purpose already exists. If one does, call `write_skill` to update it instead
  of creating a duplicate.
- Call `write_skill` with the skill name, a concise description, and the
  procedure as the content body.
- After writing, call `list_skills` to verify the skill is discoverable.

Layer 2 (periodic mid-session reflection prompt) is out of scope for v0.1.7.

### Bundled `planck_setup` skill

The `## Planck guides` section is removed from `DefaultPrompt.orchestrator/0`
and replaced with a single instruction:

```
Call load_skill("planck_setup") before answering questions about configuring Planck.
```

The guides content becomes `~/.planck/skills/planck_setup/SKILL.md`, installed at
first run. Its frontmatter:

```markdown
---
name: planck-setup
description: Guides for configuring Planck — providers, models, teams, skills, sidecars, and the HTTP API.
always_present: false
planck_version: 0.1.7
use_count: 0
last_used: null
---
```

**Upgrade logic** (`planck_headless` application start):

1. If `~/.planck/skills/planck_setup/SKILL.md` does not exist → create it with
   the bundled content and default frontmatter.
2. If it exists and `planck_version` matches the running version → no-op.
3. If it exists and `planck_version` differs → parse the existing frontmatter,
   preserve all keys, rewrite only the markdown body with the bundled content,
   update `planck_version`.

User-added frontmatter keys (e.g. a custom `always_present: true`) and usage
stats (`use_count`, `last_used`) are always preserved across upgrades.

## Phase 5 — Typesense session index (`planck_agent`, `planck_docker`)

The Docker sidecar shadows `session_search` with a Typesense-backed implementation.
The core SQLite FTS path (Phase 2) remains the default for non-Docker deployments.

### Collection

A dedicated `planck_sessions` collection, separate from the workspace file index
(`TYPESENSE_COLLECTION`). The workspace watcher already excludes `.planck/sessions`
from file indexing — no additional exclusion needed.

Schema:

```json
{
  "name": "planck_sessions",
  "fields": [
    {"name": "id",           "type": "string"},
    {"name": "session_id",   "type": "string", "facet": true},
    {"name": "team_alias",   "type": "string", "facet": true},
    {"name": "agent_name",   "type": "string", "facet": true},
    {"name": "role",         "type": "string", "facet": true},
    {"name": "content",      "type": "string"},
    {"name": "timestamp",    "type": "int64"}
  ],
  "default_sorting_field": "timestamp"
}
```

`id` is `"#{session_id}:#{db_id}"` — globally unique and stable across restarts
since each session has its own SQLite file with autoincrement IDs. Idempotent
on upsert.

### Ingestion — global broadcast + `Sidecar.SessionIndexer`

`planck_agent` adds a second broadcast on every turn end to a global
`"planck:turns"` PubSub topic alongside the existing per-agent and per-session
broadcasts:

```elixir
Phoenix.PubSub.broadcast(Planck.Agent.PubSub, "planck:turns", {:turn, team_alias, agent_name, session_id, db_id, message})
```

`Sidecar.SessionIndexer` is a new GenServer in `planck_docker/sidecar` that:

1. Subscribes to `"planck:turns"` at startup.
2. On each event, extracts searchable content: concatenates all `{:text, _}` and
   `{:thinking, _}` parts from the message; skips `{:tool_call, _, _, _}` and
   `{:tool_result, _, _}` (too noisy, not useful for recall).
3. Upserts the document to the `planck_sessions` collection.

Both `role: :user` and `role: :assistant` messages are indexed — user messages
carry the task descriptions and domain terms most useful for recall; assistant
messages carry the outcomes. Tool result messages are skipped.

User messages shorter than 20 characters (pure acknowledgments: "ok", "yes",
"do it") are skipped.

### `session_search` shadow

The sidecar registers a `session_search` tool that overrides the built-in SQLite
FTS tool. It queries Typesense filtered by `agent_name` — same semantics as the
core tool, richer results:

```
GET /collections/planck_sessions/documents/search
  ?q=<query>
  &query_by=content
  &filter_by=team_alias:=<team_alias>&&agent_name:=<agent_name>
  &per_page=10
  &sort_by=_text_match:desc,timestamp:desc
```

Returns the same format as the core `session_search` — a list of text excerpts —
so the agent prompt guidance (Phase 2) needs no changes.

## Non-goals for v0.1.7

- **SOUL.md**: not introduced — `system_prompt` in TEAM.json already serves this
  role. A future convention (e.g. a `soul.md` file path as the default
  `system_prompt` for a well-known agent type) can be added without spec changes.
- **Dynamic workers**: no memory for `spawn_agent` workers. They are task-scoped
  by design.
- **UI for memory**: no memory viewer or editor in `planck_cli`. The MEMORY.md
  file is plain text and can be edited directly.
- **Semantic/vector search**: `session_search` uses SQLite FTS in the core and
  Typesense FTS in the Docker sidecar (Phase 5). Vector/embedding-based recall
  is out of scope. Other external memory providers (Honcho, Mem0, etc.) can be
  integrated via the same sidecar tool-shadow pattern — same tool names,
  different backend, agent unaware.
- **Multi-file memory**: one MEMORY.md per agent. No tiered hot/warm split beyond
  the short-term (file) / long-term (SQLite) distinction.
