# Planck v0.3.0 — Spec

## Scope

Adds two user-facing capabilities and one breaking change to the
compactor interface:

1. **`disable-model-invocation` frontmatter** — a boolean SKILL.md
   frontmatter field that, when `true`, removes a skill from the set the
   model can load on its own (via `load_skill` / the system-prompt
   index), while keeping it in `ResourceStore` so the UI can still
   surface and dispatch it.

2. **Slash commands** — typing `/<command>` (optionally followed by
   extra text) at the start of a chat message dispatches one of three
   tiers, in precedence order:
   - **Built-in primitives** — `/clear` (delete all messages in the
     session) and `/compact [prompt]` (force a compaction pass, with an
     optional prompt injected into the compactor's delegate system
     prompt via EEx).
   - **Custom commands** — `.planck/commands/<name>/COMMAND.md` files
     with frontmatter (`name`, `description`, `disable-model-invocation`,
     `help`) and an EEx-templated body. The body is rendered with the
     user's trailing arguments and enqueued as a `{:custom, :command}`
     message.
   - **Skills** — `/skill-name [extra]` loads the named skill into the
     agent's context via `Agent.load_skill/3`, which enqueues a
     `{:custom, :skill}` message (the LLM sees the skill content as a
     `:user` message), then the user's text if provided (the
     lowest-precedence tier).

   The UI surfaces this in two places: an autocomplete dropdown
   triggered by a leading `/` (showing every command in the store —
   built-ins, custom commands, and skills, with disabled-invocation
   skills visually marked), selectable by mouse or ↑/↓ arrow keys; and a
   distinct in-chat rendering of dispatched commands so they read as
   commands rather than ordinary user messages (collapsible body,
   deletable while queued).

3. **Breaking: `compact/3 → compact/4`** — the
   `Planck.Agent.Hooks.Compactor` behaviour's `compact` callback gains a
   fourth `args` parameter (`%{prompt: String.t() | nil}`) so `/compact`
   can thread a user-supplied prompt into the summarization. This is the
   reason for the minor version bump (v0.3.0, not v0.2.6). Custom
   compactor modules must add the fourth parameter; the simplest
   migration is `def compact(state, context, recent, _args)`.

In scope:

- A `disable_model_invocation` field on `Planck.Agent.Skill.t()` and its
  frontmatter parser.
- Filtering that field out of the agent-facing skill pool at the three
  wiring points in `planck_headless`.
- Preservation of the field by the sidecar's `write_skill` tool.
- A backend dispatcher in `Headless.prompt/3` that parses
  `/<command-name> [extra]` at the start of a prompt and resolves it
  against three tiers: built-in primitives (`/clear`, `/compact`),
  custom commands (from `ResourceStore.commands`), and skills (from
  `ResourceStore.skills`, unfiltered). The primitives get new
  `Agent.clear/1` and `Agent.compact/2` GenServer calls; custom commands
  enqueue a `{:custom, :command}` message via the new `Agent.command/3`
  call with an EEx-rendered body; skills are loaded via the new
  `Agent.load_skill/3`, which enqueues a `{:custom, :skill}` message.
- **Unified command queue.** The separate `Planck.Agent.PendingCommands`
  struct (which held queued `/clear` and `/compact` as pending-flags) is
  removed. All queued operations — user messages, custom-command
  messages, and `/clear` / `/compact` primitives — now live as
  unpersisted messages in `state.messages` (`{:custom, :clear}` /
  `{:custom, :compact}` for the primitives). The turn-boundary drain in
  `maybe_turn_start` scans the list for control markers and runs them in
  precedence order (clear > compact > queued input) before starting a
  new turn. This makes queued primitives visible and deletable in the UI
  alongside queued commands, and lets `Agent.cancel_queued/2` cancel any
  of them uniformly.
- New `Planck.Agent.command/3` and `Planck.Agent.cancel_queued/2`
  GenServer calls — the former enqueues a `{:custom, :command}` message
  (replacing the `:command` opt that used to overload `Agent.prompt/3`);
  the latter removes an unpersisted message by id from the agent's
  in-memory queue (covers user, command, clear, and compact markers).
- A new `Planck.Agent.Command` module mirroring `Planck.Agent.Skill`
  (loader, frontmatter parser, `COMMAND.md` sentinel).
- A new `Planck.Agent.EExRenderer` shared helper, used by both the
  compactor's delegate system prompt and custom command bodies.
- A new `Session.clear/1` (`DELETE FROM messages`) for the `/clear`
  primitive.
- The `compact/4` callback + dispatch threading `args` through to the
  compactor (local + sidecar RPC paths).
- `Config.commands_dirs` + `ResourceStore.commands` field + `Watcher`
  coverage for custom command directories.
- A UI dropdown rendered by `PromptInput` when the textarea text starts
  with `/`, covering all three tiers in one flattened list, with keyboard
  (↑/↓/Enter/Esc) and mouse selection.
- A distinct in-chat rendering of dispatched commands: persisted
  commands render as a header chip (`/<name> <args>`) with a collapsible
  rendered body, and queued commands (while the agent is busy) render as
  deletable chips. Agent-invoked commands (the future `run_command` tool
  path) render with distinct muted/left styling.

## Objective

Give users explicit, predictable control over which skills an agent
self-loads, while providing a fast keyboard-driven way to force-load any
skill — including ones the model is no longer allowed to invoke on its
own. The `disable-model-invocation` field and the skill tier of slash
commands are complementary: the field removes a skill from the model's
autonomous reach, and `/skill-name` gives the user a way to bring it back
on demand without editing config.

Beyond skills, slash commands generalize to a full command system:
`/clear` and `/compact` as session-management primitives, and
user-authored `.md`-with-frontmatter custom commands that expand into
templated messages. This makes common workflows (clearing context,
forcing compaction with a focus prompt, running a reusable prompt
template) one keystroke away, uniformly available from both the UI and
the HTTP API.

## Use Cases

- A skill whose instructions are expensive to follow (long, multi-step)
  is marked `disable-model-invocation: true` so the model doesn't pull
  it in speculatively on every vaguely-related turn; the user types
  `/heavy-skill` when they actually want it run.
- A skill the user wants to gate behind explicit intent (destructive
  cleanup, billing actions) is disabled for model invocation and only
  ever loaded by a deliberate `/billing` keystroke — the model can't
  decide on its own to load it.
- A user mid-conversation types `/grill-me give me five hard follow-up
  questions` — the dropdown filters to matching commands as they type,
  they arrow-select `grill-me`, the skill loads as a synthetic tool call,
  and the agent receives both the skill content and the appended extra
  instruction.
- A user discovers available commands by typing `/` alone and browsing
  the dropdown, including built-ins (`clear`, `compact`), custom
  commands (with their `help` usage strings as subtitles), and skills
  (with disabled-invocation ones badged "manual").
- A long debugging session's context grows unwieldy; the user types
  `/compact focus on the API design decisions and ignore the early
  setup steps` to force a compaction pass whose summary is steered by
  the supplied prompt — without waiting for the auto-compaction
  threshold to trigger.
- A user starts fresh within the same session by typing `/clear` to wipe
  all messages (the session process stays alive, metadata preserved, no
  need to close and reopen).
- A team defines a reusable review-checklist command as
  `.planck/commands/review-checklist/COMMAND.md` with an EEx body
  templated on the scope argument; any team member types
  `/review-checklist src/auth` to expand the checklist for that scope.
- An external CI script POSTs to `/api/sessions/:id/prompt` with
  `/compact summarize the debugging steps` — the HTTP API resolves the
  slash command because parsing lives in `Headless.prompt/3`, not the
  LiveView.

## Explicitly not touched

- **Renaming or removing the `skills` array in TEAM.json.** It's carried
  through `AgentSpec.skills` → `SkillIndex.names` but is not currently
  enforced at runtime (see the `skills.md` spec note). This spec doesn't
  change that — it adds an orthogonal, enforced filter
  (`disable_model_invocation`) rather than fixing the dormant one.
  Revisit the TEAM.json `skills` filter separately if/when desired.
- **Agent (model) invocation of custom commands.** The
  `{:custom, :command}` message's `invoked_by` field is designed to
  accept `:assistant` later, but a `run_command` tool the model can call
  (for commands with `disable-model-invocation: false`) plus the
  command-pool filtering at agent wiring points are a follow-up step,
  not part of v0.3.0. The `disable-model-invocation` field on commands is
  parsed and stored in Step 4 but has no runtime effect until that
  follow-up.
- **Mid-message slash commands.** Per the user's decision,
  `/<command-name>` only triggers at the start of the message. Inline
  parsing is out of scope.
- **Persisting slash-command usage into `SkillUsage` (`.planck/skills.db`)
  for custom commands.** Only the skill tier (tier 3) records usage — it
  reuses the existing `on_use` callback path, so usage *is* recorded the
  same way a real `load_skill` call records it. Custom commands (tier 2)
  do not have a usage-tracking analog in v0.3.0; no new persistence shape
  is introduced for them.
- **The `list_skills` tool.** Still opt-in via TEAM.json, still reflects
  the filtered (post-Step-2) pool. No change.
- **Additional built-in primitives.** Only `/clear` and `/compact` are
  in scope. A general built-in registry (e.g. `/model`, `/reset`,
  `/config`) could be a follow-up.
- **Editing queued commands (re-rendering with new args).** A queued
  command can be *deleted* via `Agent.cancel_queued/2`, but not re-edited
  in place — the rendered template can't meaningfully be re-edited as
  free text. Editing support is a follow-up if needed.

## Behavioral changes worth flagging

- **Rewind drops queued `/clear` / `/compact`.** Because the primitives
  now live as unpersisted markers in `state.messages` rather than a
  separate `pending_commands` field, `Agent.rewind_to_message/2` (which
  reloads `state.messages` from the DB) silently drops any queued
  primitive. This is the intended new behavior — rewinding to inspect
  history shouldn't trigger a pending wipe — and is a change from
  v0.2.x, where `pending_commands` survived a rewind.
- **Queued `/clear` / `/compact` are now visible + deletable in the
  UI.** Previously they were silently held as pending-flags and invisible
  until the turn boundary. Unification makes them render as deletable
  chips in the chat view, the same way queued user/command messages do
  (see [Step 8](v0.3.0-spec/step-8-command-rendering.md)).

   **Resolved** — Tier 3 uses `Agent.load_skill/3` with a `{:custom, :skill}`
   message; no Session insertion API is needed.
2. **Whether disabled-invocation skills should still be reachable by
   `spawn_agent`'s `filter_granted`.** Current plan: yes — the filter in
   Step 2 only touches the static-agent wiring points, not the dynamic
   `spawn_agent` path (`tools.ex:283`), which intersects by name against
   the *full* `store.skills` pool. Confirm during Step 2; if the intent
   is that disabled skills are also hidden from orchestrator-granting,
   extend the filter there too. Left open because `spawn_agent` already
   requires the orchestrator to name skills explicitly, which is closer
   to "user-driven" than "model-autonomous".

3. **Dropdown positioning when the textarea is at the bottom of a
   scrolling chat.** The existing `FloatingDropdown` hook repositions
   *below* its trigger. A command dropdown likely needs to open *above*
   the textarea. Resolve during Step 6 with a `position: :above` option
   or a separate `CommandDropdown` hook.
