## 1. Tool Call Loop Detection

### Problem

Agents sometimes call the same tool with identical arguments repeatedly within a single turn — expecting different results. This wastes context tokens and never resolves. The root cause is usually the agent not realising it needs to change its arguments.

### Behaviour

`Planck.Agent` tracks tool calls within the current turn (messages since `stream_start`). Before executing a tool call, it checks whether the same `{tool_name, args}` pair has been called consecutively. If the count reaches `@loop_threshold` (default: **3**), a soft nudge is appended to the tool result alongside the normal output.

The nudge is not a hard stop — the agent still receives the tool result and can continue. It reads:

> "Note: you have called `{tool_name}` with identical arguments {N} times this turn and received the same result each time. If you need different information, consider changing your arguments or trying a different approach."

### Design decisions

- **Consecutive, not total** — `list_team()`, `read(file)`, `list_team()` is not a loop; three consecutive `list_team()` calls with the same args is.
- **Turn-scoped** — the counter resets at every `turn_start`. Calling the same tool across turns is fine.
- **Universal threshold** — `@loop_threshold 3` for all tools. Per-tool thresholds add complexity for little gain; the nudge is soft so false positives are harmless.
- **Appended, not replaced** — the tool result is still delivered; the nudge is appended so the agent has all the information it needs to self-correct.

### Implementation

`planck_agent/lib/planck/agent.ex`:
- Add `loop_counts: %{}` to agent state (map of `{tool_name, args_hash} → count`), reset on `turn_start`
- In `execute_tool/3`: before executing, increment count; if count >= threshold, append nudge to result
- `args_hash`: `:erlang.phash2(args)` — fast, good enough for equality detection

## 2. Agent-Vault Proxy Support

### Background

[Infisical agent-vault](https://github.com/infisical/agent-vault) is a credential-injecting MITM proxy for AI agent requests. It runs on two ports:
- **:14322** — MITM proxy (LLM requests pass through here; vault injects API keys)
- **:14321** — Management UI (user configures credentials here)

Planck routes LLM requests through the proxy; agents never see API keys directly, reducing prompt-injection credential leakage.

### Config keys (`config.json` or env vars)

| Key | Env var | Description |
|---|---|---|
| `tool_proxy` | `PLANCK_TOOL_PROXY` | HTTP proxy URL for all LLM requests (e.g. `http://vault:14322`) |
| `tool_proxy_ui` | `PLANCK_TOOL_PROXY_UI` | External URL of the proxy management UI (e.g. `http://localhost:14321`) |

Both are `String.t() | nil`. Two independent Skogsra keys with `binding_order: @json`.

`tool_proxy` is used internally (Docker network address). `tool_proxy_ui` is used by the browser (host-accessible address). They can be the same value for non-Docker setups.

### Wiring the proxy into LLM requests

`planck_ai/lib/planck/ai/adapter.ex` builds the `req` options for each LLM call. When `tool_proxy` is set, add it to the Finch/req options:

```elixir
|> then(fn opts ->
  case Config.tool_proxy() do
    nil -> opts
    proxy_url -> Keyword.put(opts, :connect_options, proxy: proxy_url)
  end
end)
```

**TLS CA cert**: agent-vault is a TLS MITM proxy — it issues its own CA certificate. Erlang's `:ssl` won't trust it by default. The CA cert must be mounted into the container and passed to the SSL options in Finch. Config key: `tool_proxy_ca_cert` (path to the PEM file). When set, add to req SSL options: `ssl: [cacertfile: ca_cert_path]`.

| Key | Env var | Description |
|---|---|---|
| `tool_proxy_ca_cert` | `PLANCK_TOOL_PROXY_CA_CERT` | Path to proxy CA certificate (PEM). Required for TLS MITM proxies. |

### UI button

When `tool_proxy_ui` is configured, show a button in the session status bar (next to ⚙) that opens the management UI in a new tab. Label: `🔐` or `vault`.

`planck_cli/lib/planck/web/live/session_live.html.heex`:
```heex
<%= if @tool_proxy_ui do %>
  <a href={@tool_proxy_ui} target="_blank" rel="noopener"
     class="border-t-2 border-l-2 border-black px-3 font-mono text-sm
            bg-card hover:bg-muted transition-colors"
     title="Open credential vault">🔐</a>
<% end %>
```

`tool_proxy_ui` passed as an assign from session_live via `Headless.config()`.

## 3. Secret Storage Hook + Agent-Vault Migration

### Problem

API keys stored in `.planck/.env` are accessible to agents, which could leak them via prompt injection. Moving them to agent-vault means agents never have access to credentials — the vault injects them directly into HTTP request headers.

### Secrets behaviour

New `Planck.Headless.Secrets` behaviour (in `planck_headless`):

```elixir
@callback store(key :: String.t(), value :: String.t()) :: :ok | {:error, term()}
@callback fetch(key :: String.t()) :: {:ok, String.t()} | :not_found | {:error, term()}
@callback list() :: {:ok, [String.t()]} | {:error, term()}
@callback delete(key :: String.t()) :: :ok | {:error, term()}
```

Two implementations:

**`Planck.Headless.Secrets.EnvFile`** (default) — reads and writes `.planck/.env` and `~/.planck/.env`. Current behaviour, unchanged.

**`Sidecar.Secrets.AgentVault`** (sidecar) — reads and writes via the agent-vault HTTP API on port 14321. Active when `tool_proxy` is set.

The active implementation is resolved at startup based on config (if `tool_proxy` is set, use AgentVault; otherwise use EnvFile).

### Auto-migration

At `planck_headless` application start, if the AgentVault implementation is active:

1. Check if `.planck/.env` or `~/.planck/.env` exists
2. If yes:
   - Log: `[Planck] Migrating API keys from .env to agent-vault…`
   - Read all `*_API_KEY` entries from `.env`
   - Store each in agent-vault via `Sidecar.Secrets.AgentVault.store/2`
   - Delete the `.env` file
   - Log: `[Planck] Migration complete. .env deleted.`
3. If agent-vault is unreachable during migration: log a warning, abort migration (keep `.env` intact)

Migration is idempotent — if `.env` is already gone, nothing happens.

### Skogsra integration

API keys (`anthropic_api_key`, etc.) currently flow through `EnvBinding`. After migration, they're no longer in `.env`. The secrets hook implementation must be called at startup to populate the process environment (or application env) before Skogsra initialises, so the existing binding chain continues to work unchanged:

```elixir
# In AppSupervisor init, before Config.preload():
Planck.Headless.Secrets.preload_to_env()
# Fetches all known secrets from active implementation and sets them as
# process env vars so Skogsra's EnvBinding picks them up normally.
```

## 4. Docker Stack — Agent-Vault Service

`planck_docker/compose.yml` gains a `vault` service:

```yaml
services:
  vault:
    image: infisical/agent-vault:latest
    restart: unless-stopped
    ports:
      - "14321:14321"   # management UI — accessible from host
    volumes:
      - vault-data:/data
    environment:
      AGENT_VAULT_MASTER_PASSWORD: ${AGENT_VAULT_MASTER_PASSWORD}

  planck:
    environment:
      PLANCK_TOOL_PROXY: http://vault:14322
      PLANCK_TOOL_PROXY_UI: http://localhost:14321
      PLANCK_TOOL_PROXY_CA_CERT: /vault-ca/ca.pem
    volumes:
      - vault-ca:/vault-ca:ro   # CA cert exported by vault on first run

volumes:
  vault-data:
  vault-ca:
```

`dev_docker.sh`: add `AGENT_VAULT_MASTER_PASSWORD` to the generated `.env`.

## Open Questions

- **CA cert distribution**: How does the vault CA cert get from the vault container to the planck container on first boot? Options: shared named volume, startup script that exports it, or mount a pre-generated cert. Needs investigation.
- **agent-vault API**: The migration implementation needs the agent-vault HTTP API reference for storing/retrieving secrets. Check the Infisical docs.
- **Port 14322 exposure**: The proxy port should NOT be exposed to the host (only used internally between planck and vault containers). Verify compose doesn't expose it.
