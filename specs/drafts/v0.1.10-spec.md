# Planck v0.1.10 — Spec

## Overview

Three areas: agent reliability (loop detection), credential security (agent-vault proxy + secret store hook), and the Docker stack update to wire them together.

### Revised design decisions (post-implementation)

- **`tool_proxy_ui` dropped** — agent-vault management UI is no longer exposed externally. Port 14321 is not published in Docker compose. All secret and service rule management happens through Planck's own modal.
- **Secrets + service rules modal** — SetupModal gains two new flows: "Manage API keys" (credentials CRUD) and "Configure a service rule" (host-scoped credential injection). Both use `Planck.Headless.Secrets` callbacks — transparent to `EnvFile` vs `AgentVault` backend.
- **Vault as internal service** — agent-vault runs as an internal Docker service only. Users never interact with it directly.
- **No credential placeholders** — `__key_name__` style placeholders are not used. They are a prompt-injection exfiltration vector (the agent could send the placeholder to an attacker-controlled host and the vault would substitute the real value). Service rules are host-scoped — the vault only injects a credential for requests going to the configured host, which the agent cannot influence.
- **Token-based vault auth** — the sidecar uses a scoped agent token (`AGENT_VAULT_TOKEN`) with `proxy` role on a single vault, not admin email/password. Bootstrap happens once in the setup container.

## 1. Tool Call Loop Detection

### Problem

Agents sometimes call the same tool with identical arguments repeatedly within a single turn — expecting different results. This wastes context tokens and never resolves. The root cause is usually the agent not realising it needs to change its arguments.

### Behaviour

`Planck.Agent` tracks tool calls within the current turn (messages since `stream_start`). Before executing a tool call, it checks whether the same `{tool_name, args}` pair has been called consecutively. If the count reaches `@loop_threshold` (default: **3**), a soft nudge is appended to the tool result alongside the normal output.

The nudge is not a hard stop — the agent still receives the tool result and can continue. It reads:

> "Note: you have called `{tool_name}` with identical arguments {N} times this turn and received the same result each time. If you need different information, consider changing your arguments or trying a different approach."

### Design decisions

- **Consecutive, not total** — `list_team()`, `read(file)`, `list_team()` is not a loop; three consecutive `list_team()` calls with the same args is.
- **Turn-scoped** — the counter resets at every `turn_start`. Calling the same tool across turns is fine.
- **Universal threshold** — `@loop_threshold 3` for all tools. Per-tool thresholds add complexity for little gain; the nudge is soft so false positives are harmless.
- **Appended, not replaced** — the tool result is still delivered; the nudge is appended so the agent has all the information it needs to self-correct.

### Implementation

`planck_agent/lib/planck/agent.ex`:
- Add `loop_counts: %{}` to agent state (map of `{tool_name, args_hash} → count`), reset on `turn_start`
- In `execute_tool/3`: before executing, increment count; if count >= threshold, append nudge to result
- `args_hash`: `:erlang.phash2(args)` — fast, good enough for equality detection

## 2. Agent-Vault Proxy Support

### Background

[Infisical agent-vault](https://github.com/infisical/agent-vault) is a credential-injecting MITM proxy for AI agent requests. It runs on two ports:
- **:14322** — MITM proxy (LLM and tool HTTP calls pass through here; vault injects credentials)
- **:14321** — Management API (internal only, not exposed externally)

Planck routes LLM requests through the proxy; agents never see API keys directly, reducing prompt-injection credential leakage.

### Config keys (`config.json` or env vars)

| Key | Env var | Description |
|---|---|---|
| `tool_proxy` | `PLANCK_TOOL_PROXY` | HTTP proxy URL for all outbound requests (e.g. `http://vault:14322`) |
| `tool_proxy_ca_cert` | `PLANCK_TOOL_PROXY_CA_CERT` | Path to proxy CA certificate (PEM). Required for TLS MITM. |
| `secrets_hook` | `PLANCK_SECRETS_HOOK` | Module implementing `Planck.Agent.Secrets`. Default: `EnvFile`. |

`tool_proxy_ui` was removed — vault management is handled inside Planck's secrets modal.

### Wiring the proxy into LLM requests

`planck_ai/lib/planck/ai/adapter.ex` builds the `req` options for each LLM call. When `tool_proxy` is set, add it to the Finch/req options:

```elixir
|> then(fn opts ->
  case Config.tool_proxy() do
    nil -> opts
    proxy_url -> Keyword.put(opts, :connect_options, proxy: proxy_url)
  end
end)
```

**TLS CA cert**: agent-vault is a TLS MITM proxy — it issues its own CA certificate. Erlang's `:ssl` won't trust it by default. The CA cert must be mounted into the container and passed to the SSL options in Finch. When `tool_proxy_ca_cert` is set, add to req SSL options: `ssl: [cacertfile: ca_cert_path]`.

## 3. Secret Storage Hook + Agent-Vault Migration

### Problem

API keys stored in `.planck/.env` are accessible to agents, which could leak them via prompt injection. Moving them to agent-vault means agents never have access to credentials — the vault injects them directly into HTTP request headers.

### `Planck.Agent.Secrets` behaviour

New behaviour in `planck_agent` (so both headless and sidecar can implement it):

```elixir
# Credentials
@callback store(key :: String.t(), value :: String.t()) :: :ok | {:error, term()}
@callback fetch(key :: String.t()) :: {:ok, String.t()} | :not_found | {:error, term()}
@callback fetch_all() :: {:ok, t()} | {:error, term()}
@callback list() :: {:ok, [String.t()]} | {:error, term()}
@callback delete(key :: String.t()) :: :ok | {:error, term()}

# Service rules
@callback store_service(host :: String.t(), auth_type :: String.t(), credential_key :: String.t(), opts :: keyword()) :: :ok | {:error, term()}
@callback delete_service(host :: String.t()) :: :ok | {:error, term()}
@callback list_services() :: {:ok, [service()]} | {:error, term()}

@type t :: %{optional(String.t()) => String.t()}
@type service :: %{
  host: String.t(),
  auth_type: String.t(),    # "bearer" | "api-key"
  credential_key: String.t(),
  header: String.t() | nil  # only for auth_type "api-key"
}
```

### Implementations

**`Planck.Headless.Secrets.EnvFile`** (default) — reads/writes `.planck/.env` and `~/.planck/.env`.

Credentials: standard `KEY=VALUE` lines.

Service rules: standalone comment lines, appended to the end of the file:

```env
N8N_API_KEY=abc123
ANTHROPIC_API_KEY=sk-ant-...

# planck-service: api.n8n.com bearer N8N_API_KEY
# planck-service: api.anthropic.com api-key x-api-key ANTHROPIC_API_KEY
```

Standard `.env` parsers (including Skogsra's EnvBinding) ignore `#` lines — no changes to `EnvBinding` needed.

`store_service/4` appends or replaces the matching `# planck-service:` line.
`delete_service/1` removes it.
`list_services/0` scans for `# planck-service:` lines and parses them.

**`Sidecar.Secrets.AgentVault`** (sidecar, Docker only) — wraps agent-vault HTTP API on port 14321.

Credentials: `POST/GET/DELETE /v1/vaults/{vault}/credentials`
Service rules: `POST/GET/DELETE /v1/vaults/{vault}/services` (see Section 5)

### `Planck.Headless.Secrets` dispatch module

Resolves the active implementation based on `secrets_hook` config. Provides the same callbacks as `Planck.Agent.Secrets`, dispatching to the active implementation. When the implementation is a remote sidecar module, dispatches via `:rpc.call/5`.

`store/2` and `delete/1` additionally call `System.put_env/delete_env` and `ResourceStore.reload()` so Skogsra picks up changes immediately.

`preload_to_env/0` — fetches all secrets and sets them in the OS process env. Called when the sidecar connects (in `SidecarManager.handle_info/2`), not at boot (Skogsra reads `.env` via EnvBinding directly).

### Auto-migration

When `AgentVault` starts and detects an existing `.env`:

1. Migrate all `KEY=VALUE` credentials to vault
2. Migrate all `# planck-service:` comment lines to vault service rules
3. Delete the `.env` file

Migration is idempotent. If vault is unreachable, abort and keep `.env` intact.

## 4. Docker Stack — Agent-Vault Service

### Compose

```yaml
services:
  setup:
    image: ghcr.io/alexdesousa/planck:0.1.10
    entrypoint: ["/setup.sh"]
    volumes:
      - ${PLANCK_HOME}/workspace:/workspace
    environment:
      SEARXNG_SECRET: ${SEARXNG_SECRET}
      SEARXNG_LANGUAGE: ${SEARXNG_LANGUAGE:-en}
      # Admin credentials — used only during setup bootstrap, never passed to planck
      AGENT_VAULT_URL: http://vault:14321
      AGENT_VAULT_EMAIL: ${AGENT_VAULT_EMAIL}
      AGENT_VAULT_PASSWORD: ${AGENT_VAULT_PASSWORD}
    depends_on:
      vault:
        condition: service_started

  planck:
    image: ghcr.io/alexdesousa/planck:0.1.10
    volumes:
      - ${PLANCK_HOME}/workspace:/workspace
      - vault-data:/vault-data:ro
    environment:
      PLANCK_TOOL_PROXY: http://vault:14322
      PLANCK_TOOL_PROXY_CA_CERT: /vault-data/ca/ca.crt.pem
      PLANCK_SECRETS_HOOK: Sidecar.Secrets.AgentVault
      AGENT_VAULT_URL: http://vault:14321
      # AGENT_VAULT_TOKEN is written to workspace/.env by the setup container
      # and loaded by Skogsra's EnvBinding at runtime — not set here explicitly
    depends_on:
      setup:
        condition: service_completed_successfully
      vault:
        condition: service_started

  vault:
    image: infisical/agent-vault:latest
    restart: unless-stopped
    volumes:
      - vault-data:/root/.agent-vault
    environment:
      AGENT_VAULT_MASTER_PASSWORD: ${AGENT_VAULT_MASTER_PASSWORD}

volumes:
  vault-data:
```

### CA cert distribution

Agent-vault generates its own CA cert on first run at `/root/.agent-vault/ca/ca.crt.pem`. The `vault-data` named volume is shared between `vault` (as `/root/.agent-vault`) and `planck` (as `/vault-data:ro`). The cert is available to planck at `/vault-data/ca/ca.crt.pem` with no copy step and no startup ordering problem.

### install scripts

`docs/install_docker.sh` and `docs/install_docker.ps1`: generate random `AGENT_VAULT_MASTER_PASSWORD`, `AGENT_VAULT_EMAIL`, `AGENT_VAULT_PASSWORD`, and `SEARXNG_SECRET` via `add_if_missing`.

`dev_docker.sh`: same random generation for local development.

## 5. Vault Service Rules

### Security rationale

Credential placeholders (`__n8n_api_key__`) are not used. They are a prompt-injection exfiltration vector: an adversarial document or tool response could instruct the agent to call `api.evil.com` with `__n8n_api_key__` in a header, and the vault would substitute the real credential, leaking it.

Service rules are host-scoped — the vault only injects a credential for requests going to the configured host. The agent cannot influence which host a service rule applies to, regardless of what the agent does or what it is told.

### Vault service rules API (confirmed from source)

| Endpoint | Description |
|---|---|
| `POST /v1/vaults/{name}/services` | Upsert rules. Body: `{"services": [{...}]}` |
| `GET /v1/vaults/{name}/services` | List rules |
| `DELETE /v1/vaults/{name}/services/{host}` | Delete rule by host |
| `GET /v1/service-catalog` | 23 built-in templates (Anthropic, OpenAI, GitHub, Stripe, …) |

Service rule object:

```json
{
  "host": "api.n8n.com",
  "auth": {
    "type": "bearer",
    "key": "N8N_API_KEY"
  }
}
```

For `api-key` type, `auth` also has `"header": "x-api-key"`.

### Hardcoded catalog

The vault's `GET /v1/service-catalog` is 23 static entries. Planck ships a hardcoded subset of common ones to keep the UI responsive and to work without a running vault (e.g. EnvFile mode):

| Env var | Host | Auth type | Header |
|---|---|---|---|
| `ANTHROPIC_API_KEY` | `api.anthropic.com` | `api-key` | `x-api-key` |
| `OPENAI_API_KEY` | `api.openai.com` | `bearer` | — |
| `GOOGLE_API_KEY` | `generativelanguage.googleapis.com` | `bearer` | — |
| `GITHUB_TOKEN` | `api.github.com` | `bearer` | — |
| `STRIPE_API_KEY` | `api.stripe.com` | `bearer` | — |

### SetupModal — ServiceStep

`ChooseStep` gains a "Configure a service rule" card. It opens a new `ServiceStep` LiveComponent:

1. **Secret key** — dropdown populated from `Secrets.list/0`
2. **Service template** — dropdown of hardcoded catalog + "Custom". Auto-selects the matching entry when a known key is selected (e.g. `ANTHROPIC_API_KEY` → "Anthropic"); falls back to "Custom"
3. **Host** — prefilled from template, editable
4. **Auth type** — `bearer` / `api-key`, prefilled from template
5. **Header** — only visible for `api-key` type, prefilled from template
6. **Save** (upsert) / **Delete** (only shown when editing an existing rule)

Changing the template selection updates host, auth type, and header fields. Selecting "Custom" clears them.

### Agent workflow

The agent makes plain HTTP calls — no credential knowledge required:

```bash
# vault injects x-api-key automatically for api.anthropic.com
curl https://api.anthropic.com/v1/messages -d '{...}'

# vault injects Authorization: Bearer automatically for api.n8n.com
curl https://api.n8n.com/api/v1/workflows
```

## 6. Token-Based Agent-Vault Authentication

### Problem

The current implementation uses `AGENT_VAULT_EMAIL`/`AGENT_VAULT_PASSWORD` (admin credentials) in the sidecar. This violates least-privilege: the sidecar only needs `proxy` access to one vault, not admin access to the entire server. Admin credentials also enable the multi-user concern — scoped tokens enable multiple Planck instances to share one vault server with per-instance isolation.

### Design

**Bootstrap (setup container, `setup.sh`):**

1. Login with admin credentials → session token
2. Create vault `"planck"` via `POST /v1/vaults` (idempotent — skip if exists)
3. Create agent `"planck-sidecar"` via `POST /v1/agents` with `proxy` role on vault `"planck"` (idempotent)
4. Write `AGENT_VAULT_TOKEN=<av_agent_token>` to workspace `.planck/.env` via `add_if_missing`

Admin credentials never leave the setup container.

**Sidecar (`Sidecar.Secrets.AgentVault`):**

- Reads `AGENT_VAULT_TOKEN` from env (loaded from workspace `.planck/.env` by Skogsra EnvBinding)
- Sends `Authorization: Bearer <token>` on all vault API calls
- No login flow, no session token caching, no 401 refresh dance

**Token rotation**: re-running the setup container with an existing `AGENT_VAULT_TOKEN` in `.env` is a no-op (`add_if_missing`). To rotate: delete `AGENT_VAULT_TOKEN` from `.env`, re-run setup.

### Changes

| Package | Change |
|---|---|
| `planck_docker` | `setup.sh` — vault bootstrap; `compose.yml` — admin creds in setup service only |
| `planck_docker/sidecar` | `AgentVault` — replace login/session with token bearer auth |
| `planck_headless` | `Config` — add `agent_vault_token` config key |
